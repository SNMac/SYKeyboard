# NGram 지수 감쇠 점수 설계

- 작성일: 2026-09-27
- 이슈: #159
- 브랜치: `feat/#159-ngram-decay-score`

## 목표

NGram 학습의 정리(삭제)와 추천 순서를 빈도 대신 최근 사용이 반영되는 점수(지수 감쇠)로 정한다.
오래 쓰지 않은 학습은 저장소에 자리가 남아 있어도 지운다.

- 자주 쓰는 표현은 순위가 안정적이고 한동안 안 써도 남는다.
- 습관이 바뀌면 며칠 안에 새 표현이 예전 표현을 추월한다.
- 한 번 쓰고 만 표현·오타는 일정 입력량 동안 다시 쓰지 않으면 지워진다.
- 순수 LRU(최근순 추천·최근순 삭제)는 채택하지 않는다.

## 현재 구조 (#157 이후, 단독 한글·영어·한영 통합 공통)

- `NGramPredictiveTextEngine`이 unigram `[String: Int]`, bigram·trigram `[String: [String: Int]]`에 빈도를 둔다.
- 상한을 넘을 때만 지운다. 시간이 지났다는 이유로 지우는 경로는 없다.
  - `pruneUnigram`: unigram이 `maxKeys`(5000, 한영 10000)를 넘으면 빈도 최솟값
  - `pruneEntries`: 한 문맥 뒤 단어가 24개를 넘으면 그 문맥의 빈도 최솟값
  - `pruneKeys`: 문맥 키가 `maxKeys`를 넘으면 총 빈도 최솟값
- 빈도는 줄지 않고 동률은 딕셔너리 순서라 사실상 무작위다. 예전에 많이 쓴 표현이 계속 위에 남고,
  저장소가 포화되면 새 표현이 들어오는 즉시 지워질 수 있다.

## 결정 사항

| 항목 | 결정 |
|---|---|
| 점수 | 쓸 때마다 +1, 입력 단어 `H`개마다 절반. 시간은 날짜가 아니라 입력 단어 수 |
| 반감기 | `H = 500`단어 |
| 잊기 | 현재 점수가 `2^(-F/H)`(`F = 10,000`단어, 즉 `2^-20`) 아래면 지운다. 상한과 무관 |
| 메모리 표현 | 선형 값 + 클록. 비교·합은 값끼리 그대로 |
| 파일 형식 | `version: 2` + `clock` + 값(`Double`). 파일 이름·위치는 그대로 |
| 옛 데이터 변환 | 빈도 비율을 유지하고 지금 반감기로 계속 써 온 점수로 옮긴다(아래 B 방식) |
| 옛 빌드로 되돌림 | 새 파일을 읽지 못해 학습이 초기화된다. App Store는 되돌릴 수 없어 TestFlight 테스터만 해당하며 감수한다 |

## 점수 모델

항목 하나의 점수는 사용 시점 `tᵢ`(누적 입력 단어 수)마다 `2^(-(clock - tᵢ)/H)`를 더한 값이다.

메모리에는 기준 시점(클록 0)으로 환산한 값을 둔다.

```
값 v = Σ 2^(tᵢ / H)
현재 점수 = v × 2^(-clock / H)
```

- 모든 항목이 같은 비율로 줄어드는 셈이라 시간이 지나도 항목 사이 순서가 바뀌지 않는다.
  비교·정렬·합은 `v`끼리 그대로 한다.
- 일정한 빈도 `r`(입력 단어당 사용 비율)로 오래 쓴 표현의 점수는 약 `r × H / ln2 ≈ 1.44 × r × H`에서 안정된다.
- 같은 빈도로 습관을 바꾸면 새 표현이 약 `H`단어 뒤에 추월한다. 일반식은 `H × log2(1 + 예전 빈도 / 새 빈도)`다.
- 쉰 표현이 잊기로 지워지기까지 입력량은 `F + H × log2(쉬기 직전 점수)`다.
  하루 10번 쓰던 표현(하루 100단어 중, 점수 약 72)은 약 13,100단어다.

## 저장 형식

```swift
// 새 형식
struct NGramData: Codable {
    var version: Int        // 2
    var clock: Double       // 누적 입력 단어 수(기준 시점 이후)
    var unigram: [String: Double]
    var bigram: [String: [String: Double]]
    var trigram: [String: [String: Double]]
}

// 옛 형식 (1.6.3 파일, #157 이전·이후 develop 파일)
struct LegacyNGramData: Codable {
    var unigram: [String: Int]
    var bigram: [String: [String: Int]]
    var trigram: [String: [String: Int]]
}
```

- 값은 메모리의 `v` 그대로 쓴다. 저장할 때 환산하지 않는다.
  저장마다 모든 값에 곱하면 10단어마다 전체 복사본이 생겨 #157 6-2의 "입력·저장 중 peak"가 커지기 때문이다.
- 클록은 입력한 단어로만 늘어나므로 키보드를 쓰지 않는 동안 점수가 줄지 않는다.
- 파일 이름과 위치(`Library/Application Support/ngram_{식별자}.plist`), 컨테이너 루트 옛 파일 이동은 그대로다.

### 로딩 순서 (백그라운드)

1. 새 형식으로 디코딩한다. 실패하면 옛 형식으로 디코딩해 변환한다. 파일이 없으면 `UserDefaults` 레거시 데이터를 변환한다.
2. `clock / H > 300`이면 모든 값에 `2^(-clock/H)`를 곱하고 `clock = 0`으로 되돌린다(`H = 500`이면 약 15만 단어에 한 번).
3. 잊기: `v < 2^((clock - F) / H)`인 항목을 지우고, 비게 된 bigram·trigram 문맥 키를 지운다.
   디코딩한 사전에서 바로 지우므로 메인 스레드 비용이 없다.
4. 메인에서 메모리에 반영한다(기존 `loadApplyScheduler` 경로).

### 옛 데이터 변환 (B 방식)

```
N = unigram 빈도 합 (0이면 배율 1)
배율 = min(1, H / (ln2 × N))
v = f × 배율, clock = 0
```

- 옛 빈도 비율(`f / N`)을 그 비율로 계속 써 왔다면 지금 가졌을 점수로 옮긴다. 기존 항목 사이의 순서는 그대로다.
- 옛 빈도를 그대로 "지금 f번 쓴 것"으로 옮기는 방식(A)은 채택하지 않았다. 빈도 500인 표현은 업데이트 뒤
  같은 빈도로 바꿔 써도 추월까지 약 2배(하루 100단어 기준 22일 vs 10일, `H = 1,000` 계산),
  빈도 5,000인 표현은 몇 달간 위에 남아, 이 이슈가 고치려는 증상이 업데이트 직후 그대로 보인다.
- 기록 단어 수가 적은 사용자(`N < H / ln2`)는 배율이 1이라 A와 같다.
- 변환 입력은 두 경로다. 모두 같은 변환 함수를 지난다.

  | App Store 빌드 | 저장 위치 | 처리 |
  |---|---|---|
  | 1.6.0 `202603151` ~ 1.6.2 `202603173` | App Group `UserDefaults` `com.snmac.sykeyboard.ngram.{ko-KR,en-US}.{unigram,bigram,trigram}` | 변환한 뒤 바로 새 형식 파일로 쓰고 키를 지운다(기존 레거시 정리 흐름 유지) |
  | 1.6.3 `202603192` | 컨테이너 루트 `ngram_{ko-KR,en-US}.plist`(옛 형식) | 기존 이동 뒤 옛 형식으로 읽어 변환하고, 다음 저장에서 새 형식으로 쓴다(`hasUnsavedChanges = true`) |

  `ngram_ko-en.plist`는 #157(develop)부터라 TestFlight 테스터에게만 있다. 형식이 같아 같은 변환을 탄다.
- 1.6.3은 문맥 키당 50개까지 저장했다. 해당 문맥에 다시 기록할 때 24개로 줄이는 지금 동작은 바꾸지 않는다.

## 기록·정리·추천·잊기

| 동작 | 변경 |
|---|---|
| 기록 `addWord` | `clock += 1` 뒤 unigram·bigram·trigram 값에 `2^(clock/H)`를 더한다. 로딩 전 `pendingEvents` 재생도 같은 경로다 |
| `endSentence` / `removeLastWord` / `resetSentenceBuffer` | 클록을 건드리지 않는다 |
| 길게 눌러 삭제 `removeWord` | 그대로 |
| 상한 정리 3종 | 구조는 그대로, `Int` → `Double`. 문맥 총점은 값의 합. 점수가 같은 경우가 사실상 없어져 "같은 빈도면 오래된 것부터" 지워진다 |
| 추천 순서 | 값이 큰 순. 순서가 시간으로 바뀌지 않으므로 `rankedUnigramCache`는 지금처럼 기록할 때만 무효화 |
| 입력 중 단어 완성 | `CaseSpellingGroup`의 표기 합산·대표 표기 선택을 `Double`로. 규칙은 그대로 |
| 잊기 | 로딩 때 한 번(위 3단계). 입력 중에는 하지 않는다 |
| 넘침 방어 | 입력 중 `clock / H > 900`이 되면 메모리에서 한 번 환산해 `clock = 0`으로 되돌린다. 엔진 하나(키보드 VC 하나)가 살아 있는 동안 45만 단어를 쳐야 오는 경계다 |

- 입력 중 잊기를 하지 않는 한계: 엔진은 키보드 VC가 만들 때마다 새로 로딩한다. 같은 VC가 계속 쓰이는 동안 기준 아래로 내려간 항목은 다음 VC 생성(로딩)까지 남는다.
  이 항목은 점수가 가장 낮아 상한 정리에서 먼저 지워지고, 후보에는 맞는 다른 단어가 없을 때만 보인다.
  코드에 `ponytail:` 주석으로 남긴다.
- 늘어나는 입력 경로 비용은 `addWord`마다 `exp2` 3번이다. `pruneKeys`는 `Int` 합 대신 `Double` 합이다.

## 반감기·잊는 기간 결정 근거

### 하루 입력량

[Putting Language into Context Using Smartphone-Based Keyboard Logging (arXiv 2403.05180)](https://arxiv.org/html/2403.05180):
독일 성인 624명(18~65세, 인구 구성 할당 표본), 최대 6개월 키보드 로깅에서 "146 words (SD=155) per user per day".
한국어 사용자 자료는 아니지만 보통 사용자를 하루 100~150단어로 보는 근거로 쓴다.
단어가 다시 쓰이는 확률이 시간의 거듭제곱 함수로 줄어든다는 결과
([Anderson & Schooler 1991](https://users.cs.northwestern.edu/~paritosh/papers/KIP/AndersonSchooler1991ReflectionsOfEnvironmentOnMemory.pdf))는
잊는 기간을 너무 짧게 잡지 않는 방향의 근거로만 참고했다(개인 키보드 입력 측정이 아니다).

### 시뮬레이션 (2026-09-27, 버리는 코드)

scratchpad에서 돌렸고 저장소에 코드는 남기지 않았다(#157과 같은 방침).

- 저장소: 한영 통합과 같은 상한(키 10000, 문맥당 24개), 넘치면 최솟값 1개를 지우는 production 규칙,
  점수는 위 선형 값 + 클록 방식.
- 입력: 한글 80%(어휘 6만)·영어 20%(어휘 2만), Zipf(s = 1.0), 문장 3~12단어. 단어마다 자주 이어지는 단어 5개를 두고
  40% 확률로 그중 하나를 쓴다.
- 탐침: 6만 단어 동안 정해진 간격으로 쓰다가 멈추고 20만 단어를 더 입력한다. seed 1·2·3의 중앙값.
- 일수는 하루 100단어 / 300단어 기준 환산.

**습관을 같은 빈도로 바꿨을 때 추월까지** (탐침 100단어마다 사용이라 계산값 `H`보다 약 100단어 이르다)

| H | 300 | 500 | 1,000 | 2,000 | 3,000 | 현재(빈도) |
|---|---|---|---|---|---|---|
| 단어 | 205 | 405 | 905 | 1,905 | 2,905 | 추월 안 함 |
| 일 | 2 / 0.7 | 4 / 1.4 | 9 / 3 | 19 / 6 | 29 / 10 | |

**가장 흔한 문맥(Zipf 1위)에서 500단어마다 쓰는 표현이 후보 첫 3칸에 있는 비율**

| H | 300 | 500 | 1,000 | 2,000 | 3,000 | 현재 |
|---|---|---|---|---|---|---|
| 비율 | 37% | 60% | 74% | 86% | 92% | 100% |

덜 흔한 문맥(20위, 41위)은 `H = 300`에서도 85~90% 이상이다.

**멈춘 표현이 상한 정리로 지워지기까지** (잊기 없음)

| H | 300 | 500 | 1,000 | 2,000 | 3,000 | 현재 |
|---|---|---|---|---|---|---|
| 흔한 문맥 속 표현(문맥당 24개) | 1,150 | 1,600 | 2,780 | 5,960 | 10,060 | 안 지움 |
| 드문 문맥 키(키 상한) | 약 4만 | 약 4만 | 약 4.1만 | 약 4.4만 | 약 4.7만 | 안 지움 |

키 상한 정리는 새 항목이 저장소를 한 바퀴 도는 속도에 달려 H와 거의 무관하다. 저장소는 3~6만 단어 뒤에 가득 찬다.

**잊기 추가 (`H = 500`)**

| 잊는 기간 F | 5,000 | 10,000 | 없음 |
|---|---|---|---|
| 멈춘 표현이 지워지기까지 | 3,200~5,100단어 | 8,200~10,100단어 | 약 4만 단어 |
| 24만 단어 뒤 저장소(unigram + bigram·trigram 쌍) | 약 9,000 | 약 16,700 | 약 63,000 |

잊는 기간은 추천 순서에 영향이 없었다(첫 3칸 비율 동일).

### 결정

- `H = 500`: 추월이 하루 146단어 기준 약 3.4일. 1,000(약 7일)은 길다고 판단했다.
  흔한 문맥에서 가끔 쓰는 표현이 밀리는 정도(60%)는 받아들인다.
- `F = 10,000`: 한 번 쓴 항목은 약 68일, 하루 10번 쓰던 표현은 약 90일 뒤 지워진다(하루 146단어).
  한 달 주기로 쓰는 표현을 지키고, 저장소는 잊기가 없을 때의 약 1/4이다.
  5,000은 저장소가 더 작지만 월 1회 표현을 매번 잊는다.

## 테스트

모두 Swift Testing이며 production 진입점(`NGramPredictiveTextEngine`)을 호출한다.
엔진 internal init에 `halfLife`(기본 500)·`forgetAfter`(기본 10,000)를 주입할 수 있게 한다(`maxKeys` 주입과 같은 방식).

- 최근 사용 반영: A를 3번 쓰고 H보다 많은 다른 단어를 친 뒤 B를 3번 쓰면 unigram·bigram 후보 모두 B가 A보다 앞
- 동률 정리: `pruneUnigram`·`pruneEntries`·`pruneKeys` 각각 같은 횟수로 쓴 항목 중 먼저 쓴 쪽이 지워짐
- 잊기: 한 번 쓰고 F 단어 넘게 다시 안 쓴 항목은 다시 로딩하면 사라지고, 기준 위 항목·문맥 키는 남음
- 저장·로딩 왕복: 순서와 클록 유지. 로딩 때 `clock / H > 300`이면 되돌린 뒤에도 순서·비율 유지
- 옛 형식 변환: 옛 `Int` 파일(기록 단어 수가 많으면 배율 적용·순서 유지, 적으면 배율 1),
  `UserDefaults` 데이터, 컨테이너 루트 옛 파일이 모두 변환되어 `version: 2`로 저장됨
- 기존 순위·정리·완성·삭제·로딩·저장 테스트는 동작 기대값을 바꾸지 않고 통과해야 한다. 저장 파일을 옛 형식으로
  직접 읽어 단언하는 곳이 있으면 새 형식으로 읽도록만 고친다. 옛 형식을 쓰는 테스트 헬퍼
  `writeNGramData`는 "옛 형식 입력" 용도로 이름과 설명을 맞춘다.
