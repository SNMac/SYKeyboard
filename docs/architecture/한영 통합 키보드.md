# 한영 통합 키보드

하나의 extension 안에서 한글과 영어를 오가는 `HangeulEnglishKeyboardViewController`의 구조를 정리한다.
관련 문서: [전체 아키텍처](전체%20아키텍처.md) · [한글 입력 로직](한글%20입력%20로직.md) · [자동완성 로직](자동완성%20로직.md)

---

## 1. 구조 — Adapter 2개 + Coordinator

한영 통합 키보드는 별도의 Core VC 없이 `BaseKeyboardViewController`를 직접 상속하고,
한글/영문 키보드의 InputAdapter를 **둘 다** 들고 있다. 새 입력 로직을 만들지 않고
단일 언어 키보드가 쓰는 Adapter를 그대로 재사용하는 구조다.

```
HangeulEnglishKeyboardViewController (Keyboards/HangeulEnglishKeyboard/Presentation/)
├── hangeulAdapter: HangeulKeyboardInputAdapter     (showsLanguageSwitchButton: true)
├── englishAdapter: EnglishKeyboardInputAdapter     (showsLanguageSwitchButton: true)
└── modeCoordinator: HangeulEnglishKeyboardModeCoordinator
    └── KeyboardLanguageModePolicy                  (언어 판정 규칙)
```

모든 오버라이드 지점(`insertPrimaryKeyText`, `deleteBackward`, `insertSpaceText`, …)은
`modeCoordinator.currentMode`로 분기해 해당 언어의 Adapter로 라우팅한다.
한글 모드일 때의 동작은 `HangeulKeyboardCoreViewController`와 동일한 패턴이다
(Adapter 호출 → `applyCompositionTransition`으로 proxy 편집 적용).

### primaryKeyboardView vs primaryKeyboardViews

```swift
override var primaryKeyboardViews: [PrimaryKeyboardRepresentable] {
    return hangeulAdapter.primaryKeyboardViews + [englishAdapter.primaryKeyboardView]  // 양쪽 전부
}
override var primaryKeyboardView: PrimaryKeyboardRepresentable {
    // 현재 mode의 뷰 하나
}
```

- `primaryKeyboardViews`(복수)는 **설치할 뷰 전체**다. `KeyboardView`가 두 언어 뷰를 모두 겹쳐 설치하고,
  버튼 액션·제스처 등록도 양쪽 모두에 걸린다. 한영 전환 버튼 갱신도 이 목록을 순회한다.
- `primaryKeyboardView`(단수)는 **현재 표시할 뷰**다. `updateShowingKeyboard()`가 이 값 기준으로 `isHidden`을 전환한다.
  클립보드 패널이 열려 있으면(`isClipboardPanelVisible`) 언어·기호·숫자·텐키 뷰를 모두 숨기고 `clipboardHistoryPanelView`만 보인다.
- 키보드 전환 버튼 팬 제스처(`SwitchGestureController`)는 한글/영어 대상 뷰를 따로 받으므로
  `hangeulSwitchGestureKeyboardView`/`englishSwitchGestureKeyboardView`를 각 Adapter의 뷰로 오버라이드한다
  (Base 기본값은 둘 다 `primaryKeyboardView`).

언어별 mode 판단이 필요한 공통 훅도 mode에 따라 갈린다:

| 오버라이드 | 한글 모드 | 영어 모드 |
|---|---|---|
| `shouldDeferUndoRedoCommit` | 조합 중이면 `true` | `false` |
| `smartQuoteRule` | `.koreanSystem` (따옴표 토글 상태 기반) | `.englishSystem` (앞 문자 기반) |
| `treatsDefaultSmartQuotesAsEnabled` | `true` | `false` |

## 2. 언어 결정 — KeyboardLanguageModePolicy

텍스트 필드가 기대하는 언어를 알려주는 공개 API는 없다. 입력 trait로 확실하게 알 수 있는 것은
"이 필드는 라틴 문자를 원한다"뿐이므로, 한글 여부는 추측하지 않고 라틴 강제 조건만 가려낸다.

```
requiresLatinInput(keyboardType:textContentType:)
├── keyboardType: .asciiCapable, .asciiCapableNumberPad, .emailAddress, .URL → true
└── textContentType: .emailAddress, .URL, .username, .password, .newPassword,
                     .oneTimeCode, .creditCardNumber → true
(webSearch·twitter·namePhonePad는 한글 입력이 자연스러운 경우가 있어 제외)

initialMode(requiresLatinInput:lastMode:preferredLanguages:)
├── 라틴 강제 필드      → .english
├── 저장된 마지막 언어   → 그 언어
└── 없으면              → OS 언어 설정(Locale.preferredLanguages)에서 ko/en 중 먼저 나오는 쪽 (기본 .hangeul)
```

- **키보드 시작 시**: `init`에서 `initialMode`로 결정한다. 이 시점에는 `textDocumentProxy`에 접근하지 않는다
  (수명주기 크래시 경로 회피). 그래서 시작 mode는 필드 trait(`requiresLatinInput`)을 보지 않는다.
  이후의 trait 반영은 trait 변화가 감지되어 `inputTraitsDidChange()`가 불릴 때만 이뤄진다.
  비교 기준인 `oldKeyboardType`/`oldTextContentType`은 lazy라 첫 접근 시점의 proxy 값으로 초기화된다.
  실기기(iPhone 15 Pro Max, iOS 27.0)에서는 새 프로세스의 첫 필드에서도
  `loadView → viewDidLoad → textWillChange → textDidChange → inputTraitsDidChange()` 순으로 훅이 불렸고,
  이메일 필드(`keyboardType=7`)는 `requiresLatinInput=true resolved=english`, Safari 주소창(`keyboardType=10`)은
  `requiresLatinInput=false resolved=hangeul`로 판정됐다(`recordLanguageModeDecision`의 `languageMode …` 로그로 확인).
  따라서 시작 mode는 첫 `textDidChange`에서 필드 trait을 반영한다.
- **필드 전환 시**: `textDidChange` → Base가 `keyboardType`/`textContentType` 변화를 감지하면 `inputTraitsDidChange()` 훅 호출 →
  `modeCoordinator.modeForInputTraitsChange`가 `initialMode`를 다시 계산한다. 키보드 extension에서는 콜백의 `textInput`이
  항상 nil이라 필드 객체로는 전환을 알 수 없어서([전체 아키텍처 §7](전체%20아키텍처.md)) trait 변화를 신호로 쓴다.
  trait이 바뀌지 않으면 훅이 불리지 않으므로 현재 mode가 유지된다. 식별자 기반 `modeForTextInputChange`는
  Coordinator에 남아 있지만 production에서는 호출하지 않는다.
- **수동 전환**: 한영 전환 버튼(`LanguageSwitchButton`) 탭.

마지막 언어는 `UserDefaultsManager.lastHangeulEnglishLanguageMode`에 저장된다.
단, **필드가 강제한 영어는 사용자의 선택이 아니므로 저장하지 않는다**(`persist: !requiresLatinInput`).
저장값이 아예 없는 상태와 기본값을 구분하기 위해 `hasLastHangeulEnglishLanguageMode`로 키 존재를 확인한다.

언어 판정 근거(필드 trait, resolved mode)는 Crashlytics에 로그로 남긴다. 입력한 텍스트는 남기지 않는다.

## 3. 언어 전환 절차 — applyLanguageMode

수동 전환과 자동 전환 모두 `applyLanguageMode(_:persist:outgoingMode:isManualSwitch:)` 한 곳으로 모인다.

```
1. stopInputInteractionsForLanguageChange()      ← 반복 입력·눌린 버튼·Shift 상태 종료 (Base)
2. 이전 언어 Adapter 정리
   ├── 한글: finishForLanguageChange() (조합 버퍼 리셋) + commitDeferredUndoRedoGroupIfNeeded()
   └── 영어: finishForLanguageChange() (Shift/CapsLock 초기화)
3. modeCoordinator.selectModeManually(mode)
4. persist면 lastHangeulEnglishLanguageMode 저장
5. primaryLanguage = mode.languageIdentifier      ← UIInputViewController 속성 ("ko-KR"/"en-US")
6. updateSuggestionLanguage(to:)                  ← SuggestionController.updateLanguage (아래 §5)
7. 한영 전환 버튼(`LanguageSwitchButton.updateLanguageMode`)·기호/숫자 키보드의 전환 버튼
   (`SwitchButton.updatePrimaryLanguageMode`) 라벨 갱신
8. KeyboardLanguageModePolicy.shouldReturnToPrimaryKeyboard 판정
   ├── 수동 전환               → 항상 문자 키보드로 복귀
   └── 자동 전환(필드 변경 등) → 기호/숫자/텐키 화면이면 그대로 유지
   ※ inputTraitsDidChange()는 textDidChange에서 updateKeyboardType() 뒤에 불린다. updateKeyboardType()이 바뀌기 전
     언어로 currentKeyboard를 한 번 정하고, 이 단계가 새 언어의 문자 자판으로 다시 정한다. 문자 자판 네 종류에는
     이 판정이 항상 true라는 성질에 기대며 testAutomaticSwitchUpdatesPrimaryKeyboard가 고정한다
9. Shift/스페이스 버튼 상태 갱신
```

한/A 전환은 자판과 `primaryLanguage`, TextChecker 조회 언어만 바꾼다. 후보 바·대치 이력·NGram 문장
버퍼는 전환 절차가 비우지 않고 그대로 유지되며, 한글 조합 중이었다면 이전 언어 Adapter 정리(2단계)가
조합을 확정한다. 후보 바가 NGram 후보를 보이는 중이면 unigram 순서만 새 언어의 문자 종류 우선으로
다시 정렬된다(§5). 입력 중 후보는 다시 계산하지 않는다.

## 4. inputBuffer 공유 — 언어 경계 없음

Base의 `inputBuffer`는 하나뿐이고 두 언어가 그대로 공유한다. 언어를 바꿔도 버퍼를 자르거나 표시하지
않으므로, 단어 완성·대치/복구·수식 인식·NGram 기록/조회/삭제 뒤 문장 버퍼 동기화·NGram 후보 앞 공백
삽입 여부(`KeyboardSuggestionSelectionPolicy.shouldInsertLeadingSpaceBeforeNGramSuggestion(inputBuffer:)`)
등 모든 입력 보조가 전체 `inputBuffer`를 그대로 본다. 단일 언어 키보드와 동일한 경로이며, 한영 통합
키보드만의 별도 분기가 없다.

후보 선택 시 NGram에 기록하는 단어도 마찬가지로 통째로 기록한다. 입력 중 모드 후보 교체는
`recordWord(result.insertText)`로 선택한 텍스트 전체를 한 단어로 기록하고(여러 단어로 된 후보도 공백을
지우지 않고 그대로 기록하는 것이 의도된 동작), 현재 단어 확정은 `KeyboardSuggestionSelectionPolicy.currentWordForConfirmation(inputBuffer:)`가
돌려주는 현재 단어를 학습·기록한다.

**알려진 한계**: `SY키보`처럼 한글과 영문이 섞인 토큰은 언어 경계로 나누지 않고 `UITextChecker`에
통째로 넘어가므로 단어 완성이 약하다. 타이핑 중 NGram 완성(#158)이 이를 보완할 예정이다.

## 5. 자동완성 엔진의 언어 전환

`SuggestionController`는 textChecker 엔진을 `[언어코드: 엔진]`으로, n-gram 엔진을 `[NGram 식별자: 엔진]`으로
캐시한다. 한글/영문 키보드는 NGram 식별자가 `language`(=언어코드)와 같지만, 한영 통합 키보드는
`nGramLanguage`로 고정한 `"ko-en"` 하나를 두 언어가 함께 쓴다(`activeNGramLanguage`).

```
updateSuggestionLanguage(to:) → SuggestionController.updateLanguage(to:)
├── nGramLanguage != nil(한영 통합 키보드): language 프로퍼티(TextChecker 조회 언어)만 바꾸고
│     refreshNGramSuggestionsForLanguageModeChange() 뒤 반환
│     └── NGram 후보를 보이는 중이면 새 선호 문자 종류로 다시 조회, 순서가 달라졌을 때만 delegate 전달
└── nGramLanguage == nil(단독 키보드):
      ├── 이전 언어 n-gram을 saveToDisk()로 즉시 보존 (엔진은 캐시에 유지 → 재전환 시 디스크 재로드 없음)
      ├── engineGeneration += 1     ← 이전 언어의 비동기 로드 완료 콜백 무효화
      └── 후보·수식 상태 초기화 (lastSuggestionBaseText 등 리셋 + clearSuggestions())
```

한영 통합 키보드는 `saveToDisk()`/`engineGeneration += 1`도, 후보·수식 상태 초기화도 하지 않는다.
두 언어가 같은 NGram 엔진 인스턴스를 계속 쓰므로 저장할 "이전 언어"가 따로 없고, 문장 버퍼
(`currentSentenceWords`)·현재 후보·수식 상태 모두 전환 뒤에 그대로 유지된다. §3의 전환 절차가
후보를 비우지 않는 것과 같은 이유다.

NGram 후보를 보이는 중(`currentMode == .nGram`)에만 마지막 요청값(`lastSuggestionBaseText`)으로 다시 조회해
unigram 순서를 새 언어의 문자 종류 우선으로 바꾼다. iOS는 한/A 전환 뒤 `textWillChange`/`textDidChange`를
보낼 때도(필드 포커스·탭 직후), 안 보낼 때도(키보드로 입력한 뒤) 있어서 그 콜백에 기대지 않고 여기서 직접
갱신한다. 입력 중 후보(`.typing`)는 다시 계산하면 다른 언어 사전으로 조회해 "자판만 바뀐다"는 원칙이 깨지므로
그대로 두고, 문맥(trigram/bigram) 후보처럼 순서가 같으면 다시 전달하지 않는다.

- lexicon 엔진은 언어 구분이 없으므로 하나를 공유한다.
- 메모리 경고 시 `releaseInactiveLanguageEngines()`가 현재 언어가 아닌 캐시만 해제한다. 통합 키보드는
  n-gram 엔진이 하나뿐이라 항상 유지되고, 비활성 TextChecker 캐시만 해제된다.
  (단독 키보드의 비활성 n-gram 엔진은 전환 시점에 이미 저장되었고 그 뒤로 학습을 받지 않으므로 유실이 없다.)
- n-gram 데이터 파일도 식별자별로 분리된다: 단독 키보드는 `ngram_ko-KR.plist` / `ngram_en-US.plist`
  (전체 키 최대 5000개), 한영 통합 키보드는 `ngram_ko-en.plist`(전체 키 최대 10000개, 두 언어가 한
  파일을 나눠 쓰므로 단독 키보드 두 엔진분 용량에 맞춘다) 하나다
  (App Group 컨테이너의 `Library/Application Support/` 아래. 옛 루트 위치 파일은 한 번 이동한다).
  기존 `ngram_ko-KR.plist`/`ngram_en-US.plist` 학습 데이터는 `ngram_ko-en.plist`로 합치지 않는다.
  통합 키보드는 빈 파일에서 새로 학습을 쌓는다.

상세는 [자동완성 로직 §5](자동완성%20로직.md) 참조.

## 6. 영문 입력 — EnglishKeyboardInputAdapter

영문 입력에는 조합이 없으므로 Adapter는 텍스트를 만들지 않는다.
VC가 `insertTypedText(_:)`(Smart Punctuation 적용)로 직접 입력하고, Adapter는 상태만 관리한다.

- **Shift/CapsLock**: `EnglishKeyboardView`가 보유하고 Adapter가 노출(`isShifted`/`isCapsLocked`).
- **자동 대문자** (`updateAutocapitalization`): Shift 버튼이 눌려 있지 않을 때, 설정이 켜져 있으면
  `autocapitalizationType`에 따라 Shift를 갱신한다.

| autocapitalizationType | Shift 켜는 조건 |
|---|---|
| `.allCharacters` | 항상 |
| `.sentences` | 커서 앞이 문장 시작 (마지막 마침표 뒤 공백만 있음) |
| `.words` | 커서 앞이 공백/비어 있음 |

- **대문자 입력 직후 Shift 해제**: `recordInsertedText(_:)`가 대문자 입력을 기록하면
  다음 `updateAutocapitalization`에서 함께 해제된다. (같은 결과를 위해 키 라벨 전체 갱신이 두 번 돌지 않도록
  해제와 자동 대문자 판정을 한 메서드에 묶어 두었다.)
  `EnglishKeyboardView`의 Shift 버튼 뗌 액션도 같은 플래그를 보지만, **CapsLock 중에는 누른 채 글자를 입력했더라도
  떼는 동작으로 해제하지 않는다.**

단일 영문 키보드(`EnglishKeyboardCoreViewController`)도 같은 Adapter를 쓴다.

## 7. 부가 요소

- **전체 접근 안내 오버레이** (`RequestFullAccessOverlayView`): `SYKeyboardCore`의 `BaseKeyboardViewController`가
  `viewDidLoad`에서 `needToShowFullAccessGuide`(전체 접근 꺼짐 + 아직 닫지 않음)일 때 설치하므로 세 extension 공통이다.
  닫음 여부는 App Group이 아닌 **프로세스 로컬** `UserDefaults.standard`(`KeyboardExtensionLocalStateStore`)에 저장되어
  extension별로 따로 기억된다. 앱 미리보기에서는 표시하지 않는다.
- **Firebase/Crashlytics**: 단일 한글/영문 키보드와 같은 패턴으로, `init`에서 가장 먼저 설정해
  `loadView`/`viewDidLoad` 크래시도 기록한다. `KeyboardDiagnostics.record`를 Crashlytics 로그로 연결하며,
  진단 메시지에 입력 텍스트는 포함되지 않는다.
