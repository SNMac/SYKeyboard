# 성능 고려 사항

키보드 extension은 키 입력마다 main thread에서 도는 코드가 곧 입력 지연이다. 이 문서는 지금까지 어떤 경로에서
어떤 성능 결정을 했고 왜 그랬는지, 기준값과 측정값, 하지 않기로 한 것, 새 기능을 넣을 때 확인할 항목과 측정 방법을
정리한다. 동작 설명은 현재 코드 기준이고, 측정값은 기록에 남은 값만 날짜·기기·빌드 조건과 함께 옮겼다.
측정하지 않은 값은 추정이라고 표시했다.
관련 문서: [전체 아키텍처](전체%20아키텍처.md) · [자동완성 로직](자동완성%20로직.md) · [한글 입력 로직](한글%20입력%20로직.md) ·
[삭제와 실행취소 로직](삭제와%20실행취소%20로직.md) · [한영 통합 키보드](한영%20통합%20키보드.md)

## 1. 원칙과 예산

| 원칙 | 내용 |
|---|---|
| 프레임 예산 | 120Hz 한 프레임은 8.3ms, 60Hz(iPhone 8 등 iOS 16 지원 기기)는 16.7ms다. 키 입력 하나가 main thread에서 쓰는 시간은 이 안에 들어야 키 반응이 한 프레임 이상 밀리지 않는다. 자동완성 같은 부가 기능 하나가 쓸 수 있는 몫은 그 절반으로 본다(§3-1) |
| 계측 먼저 | 바꾸기 전에 `OSSignposter` 구간을 두고 실기기 Release 빌드로 잰다. 추정으로 최적화하지 않는다(§6) |
| 결과를 바꾸지 않는 최적화 | 사전 거르기·캐시·생략 조건은 결과가 이전 코드와 같아야 한다. 이전 코드와 나란히 돌려 비교하고, 버그를 일부러 심어 테스트가 잡는지 확인한다(§6-4) |
| 비용 상한 | 학습 데이터·후보·이력에 상한을 두고, 정상 경로가 상한을 1개 넘을 때는 전체 정렬 대신 최솟값 1개만 찾는다 |
| main thread 밖으로 | 한 프레임보다 오래 걸릴 수 있는 일(시스템 사전 조회, 디스크 I/O)은 전용 큐로 보내고, 낡은 결과는 세대 검사로 버린다 |
| 설정 토글에 재생성 금지 | 필드 전환마다 바뀌는 상태(`isSuspended`)는 엔진을 해제·재생성하지 않는다 |
| 메모리 | extension 메모리 한도를 의식해 항목 상한, 이미지 디코드 예산, 메모리 경고 시 캐시 해제를 둔다 |

## 2. 경로별 결정과 이유

### 2-1. 키보드 로딩

키보드가 뜨는 시간은 `loadView` → `viewDidLoad` → `viewWillAppear` → `viewDidAppear`의 main thread 동기 비용이다.
각각 `KeyboardLoadView`, `KeyboardViewDidLoad`, `KeyboardViewWillAppear`, `KeyboardViewDidAppear` signpost 구간이 있다.

| 결정 | 이유 | 위치 |
|---|---|---|
| 예측 엔진 생성을 첫 `viewDidAppear`로 미룬다 | `UITextChecker` 생성과 NGram 파일 로드가 키보드 표시를 늦추지 않게 한다. `viewDidLoad`는 설정값만 `SuggestionController`에 전달한다 | `BaseKeyboardViewController.startDeferredSuggestionPreparationIfNeeded()` (`DeferredSuggestionPreparation` 구간), `SuggestionController.preparePredictiveEnginesIfNeeded()` |
| lexicon은 텍스트 대치가 켜져 있을 때만 `viewDidLoad`에서 먼저 요청한다 | 첫 스페이스에서 대치가 동작해야 하므로 표시 전에 시작한다. 자동완성만 켜져 있으면 첫 표시 뒤에 요청한다 | `KeyboardSuggestionSelectionPolicy.shouldStartLexiconLoadBeforeFirstAppearance` |
| NGram 파일은 백그라운드에서 읽고, 로드 전 기록은 버리지 않는다 | 파일 로드가 main을 막지 않게 `DispatchQueue.global(qos: .userInitiated)`에서 읽고 main에서 반영한다. 완료 전 조회는 빈 배열이고, 기록은 `pendingEvents`에 쌓았다가 순서대로 재생한다. 완료 콜백은 `onLoadCompleted`로 후보를 다시 계산한다 | `NGramPredictiveTextEngine.startBackgroundLoad()` (`NGramBackgroundLoad` 구간) |
| 로드 완료 후 후보 갱신은 한 프레임 뒤에 한다 | 엔진의 로딩 완료 클로저 안에서 후보 갱신이 엔진으로 재진입하지 않게 `Task { @MainActor }`로 미룬다. 한 프레임을 아끼는 대신 재진입 위험을 지는 거래라 비동기를 유지한다 | `SuggestionController.preparePredictiveEnginesIfNeeded()`의 `onLoadCompleted` |
| 한글 처리기와 자판 뷰는 `lazy`로 선택된 한 종류만 만든다 | 나랏글·천지인·두벌식 중 설정된 자판만 생성한다 | `HangeulKeyboardInputAdapter` |
| 자동완성 엔진 생성 지연은 `SuggestionController`가 아니라 VC가 시작한다 | 미리보기(`isPreview`)에서는 엔진을 만들지 않는다 | `startDeferredSuggestionPreparationIfNeeded()`의 첫 guard |

**현재 상태에서 지연되지 않는 것.** `KeyboardView`의 기호·숫자·텐키 자판과 클립보드 기록 패널은 `lazy var`로
선언돼 있지만 `setHierarchy()`가 전부 `addSubview`하므로 XIB 로드 시점(`KeyboardLoadView` 구간)에 모두 만들어진다.
클립보드 기록 설정이 꺼져 있어도 패널 뷰는 생성된다. 이 비용은 측정한 기록이 없다.

### 2-2. 키 입력

키 입력 한 번에 main thread에서 도는 것은 한글 조합 → 프록시 반영 → 자동완성 갱신 순서다.

**한글 조합과 프록시 반영**

| 결정 | 이유 | 위치 |
|---|---|---|
| 두 버퍼 구조로 프록시 조작을 O(1)로 유지한다 | `committedBuffer`는 건드리지 않고 `composingBuffer`(1~2글자)만 지우고 다시 쓴다. 텍스트 길이와 무관하게 비용이 일정하다. 처리기에는 `committedBuffer.suffix(2)`만 넘긴다 | [한글 입력 로직 §2](한글%20입력%20로직.md), `HangeulCompositionState` |
| 종성 복원으로 확정 글자를 소비하면 삭제 수를 합쳐 `.replace` 하나로 만든다 | `consumedCommittedCount`를 삭제 수에 더해 프록시 호출 횟수를 줄인다 | `HangeulCompositionState.applyCompositionResult` |
| 조합 결과가 기존 composing을 그대로 확정하면 delete·reinsert 없이 새 composing만 `.insert`한다 | 불필요한 삭제·재삽입을 피한다 | `HangeulCompositionState` |

**자동완성 갱신 (`SuggestionController.performUpdateSuggestions`)**

두 단계 갱신의 흐름은 [자동완성 로직 §3-3](자동완성%20로직.md)에 있다. 여기서는 성능 결정만 적는다.

| 결정 | 이유 | 위치 |
|---|---|---|
| lexicon은 로드 시 `userInput.lowercased()` 키 사전을 만들어 O(1)로 조회한다 | 키 입력마다 lexicon 전체를 순회하지 않는다. 결과의 순서와 내용은 순회와 같다(#123) | `LexiconPredictiveTextEngine.entriesByLowercasedInput` (`LexiconSuggestions`, `TextReplacementMatch` 구간) |
| NGram 입력 중 단어 완성은 main에서 동기로 조회한다 | NGram 저장소는 main에서만 바뀌므로 큐로 넘기지 않는다. 대신 조회 비용에 기준(§3-1)을 두고 사전 거르기로 지킨다 | `NGramPredictiveTextEngine.completions(forTypedWord:previousWord:limit:)` (`NGramCompletions` 구간) |
| unigram 전체(최대 10000개)를 훑되, 첫 유니코드 스칼라로 소문자 변환 전에 거른다 | Time Profiler에서 시간의 88%가 판정이었고 그 안에서 `lowercased()` 28%, 글자 단위 `hasPrefix` 20%, 첫 자모 계산 13%였다. 첫 글자부터 안 맞는 단어도 이 비용을 다 치렀다. 첫 스칼라가 ASCII·완성형 음절·호환 자모면 소문자 변환이 자명하므로 그 자리에서 버린다. 켈빈 기호 K·İ·É처럼 소문자 변환으로 첫 글자가 바뀌는 문자와 첫가끝 자모는 거르지 않고 원래 비교로 넘긴다(`"가\u{11A8}"`은 `"각"`과 정규 등가) | `PredictiveTextCompletionMatchPolicy.isCompletion`, `quickFirstJamo` |
| 입력과 후보가 모두 단순 스칼라면 문자열·글자·자모 배열 없이 스칼라로 판정한다 | 스칼라 하나가 곧 글자 하나이고 소문자 변환이 자명한 경우다. 결합 문자가 하나라도 섞이면 원래 비교로 넘긴다 | `PredictiveTextCompletionMatchPolicy.simpleIsCompletion` |
| 대소문자가 없는 단어(한글, 숫자)는 표기 묶기를 거치지 않고 바로 순위에 넣는다 | 소문자로 바뀌어 같아질 다른 표기가 없다. 빈도가 같은 후보의 순서를 빼면 결과는 같다 | `PredictiveTextCompletionMatchPolicy.hasNoCaseVariants` |
| 표기가 하나인 묶음은 표기별 사전을 만들지 않는다 | 영어 데이터에서는 맞는 단어 전부가 표기 묶기를 거친다. Time Profiler에서 표기 묶기가 약 60%였고, 대부분은 표기가 하나라 규칙과 관계없이 그 표기가 대표다 | `CaseSpellingGroup.representative` |
| bigram 후보가 없으면 중복 검사를 건너뛴다 | 그때 `seen`에는 입력 단어뿐이고 입력 단어는 판정 정책이 이미 뺀다 | `completions`의 `results.isEmpty \|\| !seen.contains(...)` |
| 판정 정책은 입력 단어당 한 번만 만든다 | `head`, `lastJamo`, `requiredFirstJamo` 등을 init에서 계산하고 unigram 수만큼 `isCompletion`을 재사용한다 | `PredictiveTextCompletionMatchPolicy.init` |
| `UITextChecker` 조회는 전용 직렬 큐(`.userInitiated`)로 보내고 세대 검사로 낡은 요청을 버린다 | 조회 한 번이 12~22ms라 한 프레임을 넘는다(§3-2). 큐에 밀려 있는 동안 새 입력이 오면 조회 자체를 건너뛰고, main에 돌아와서도 세대와 모드가 같을 때만 반영한다. 기다리는 동안은 직전 typing 모드의 textChecker 후보만 이어받아 빈 프레임을 막는다 | `SuggestionController.textCheckerQueue`, `textCheckerRequestGeneration`(`OSAllocatedUnfairLock`) |
| lexicon과 NGram 완성이 9칸(`maxSuggestions - 1`)을 채우면 TextChecker를 부르지 않는다 | 결과에 기여할 수 없는 조회다 | `performUpdateSuggestions`의 `maxSuggestionSlots` guard |
| `completions`로 칸이 차면 `guesses`를 부르지 않는다 | 두 호출 비용이 거의 같아 최대 절반을 아낀다. 짧은 접두어·오타·한글에서는 여전히 `guesses`까지 간다 | `TextCheckerPredictiveTextEngine.suggestions(for:limit:)` (`TextCheckerCompletions`, `TextCheckerGuesses` 구간) |
| 커서 드래그 중에는 `textDidChange`의 후보 갱신을 건너뛴다 | 드래그가 끝날 때 한 번만 갱신한다 | `KeyboardSuggestionSelectionPolicy.shouldUpdateSuggestionsOnTextDidChange` |
| 프록시 문맥은 256자까지만 읽는다 | 긴 문서에서 `documentContextBeforeInput` 처리 비용에 상한을 둔다 | `KeyboardTextContextNavigator.maximumCursorRestoreDistance`, `KeyboardSuggestionSelectionPolicy.limitedDocumentContextBeforeInput` |
| 수식 판정은 끝 글자가 `=`가 아니거나 256자를 넘으면 즉시 끝낸다 | 매 키 입력마다 도는 탐지라 parser에 들어가기 전에 거른다. 괄호 중첩은 16단계까지다 | `MathExpressionCompletionEvaluator.maximumInputLength`, `maximumNestingDepth` |

한 키 입력에서 `textInteractionDidPerform`과 호스트의 `textDidChange`가 둘 다 `updateSuggestions()`를 부를 수 있다.
같은 텍스트로 들어온 요청을 거르는 로직은 없다. 호스트가 매 키마다 `textDidChange`를 보내는지는 코드만으로 알 수
없으므로, 갱신 비용을 줄이는 변경은 실기기에서 호출 횟수를 먼저 센다.

### 2-3. 스페이스·리턴 (NGram 기록과 저장)

| 결정 | 이유 | 위치 |
|---|---|---|
| 기록마다 상한을 1개 넘는 정상 경로는 전체 정렬 없이 최솟값 1개만 찾는다 | 가득 찬 저장소에서는 trigram 새 문맥이 거의 매 스페이스마다 생긴다. 시뮬레이터 측정에서 `addWord` 시간의 약 98%가 `pruneKeys`였다(§3-3). unigram도 같은 방식이다(#123) | `NGramPredictiveTextEngine.pruneKeys`, `pruneUnigram` |
| 다음 단어 예측의 unigram 순위는 top-k 선별 후 문자 종류별로 캐시한다 | 전체 정렬 대신 상위 `maxPredictions`(10)개만 유지하고, `unigramStore`가 바뀔 때(`didSet`)만 무효화한다 | `rankedUnigramCache` (`RankedUnigramCandidates` 구간, 캐시 적중이면 구간 없음) |
| 저장은 main 스냅샷과 백그라운드 인코딩으로 나눈다 | 세 저장소를 `NGramData`로 캡처(copy-on-write라 대개 싸다)한 뒤 `.utility` 직렬 큐에서 바이너리 plist로 인코딩·atomic 쓰기 한다 | `saveToDisk()` (`NGramSaveSnapshot`, `NGramSaveEncode` 구간) |
| 변경이 없으면 저장하지 않는다 | `hasUnsavedChanges` dirty flag. 쓰기에 실패하면 다시 true로 돌려 다음에 재시도한다. 레거시 정리가 남아 있으면 dirty가 아니어도 통과시킨다 | `saveToDisk()` |
| 저장 주기는 시간이 아니라 횟수다 | `addWord` 10회마다(`writePeriod`) + `endSentence()`(리턴) + `removeWord` + 언어 전환 + `viewWillDisappear` | `scheduleSave()` |
| 이미 기록한 단어는 다시 기록하지 않는다 | 미확정 단어 기록은 `currentSentenceWordsCount`만큼 건너뛴다 | `SuggestionController.recordUncommittedWords` |

### 2-4. 삭제

삭제 확정 파이프라인과 반복 삭제의 구조는 [삭제와 실행취소 로직](삭제와%20실행취소%20로직.md)에 있다.

| 결정 | 이유 | 위치 |
|---|---|---|
| 반복 삭제·반복 입력 중에는 후보를 갱신하지 않는다 | tick마다 자동완성이 돌면 반복 속도를 못 따라간다. 손을 떼면 `repeatTextInteractionDidPerform`에서 한 번 갱신한다 | `BaseKeyboardViewController.textInteractionDidPerform`의 `isRepeatingInput` 분기 |
| 반복 삭제는 조합 재계산 없이 `.delete(count: 1)`만 한다 | tick 하나에 삭제는 정확히 한 번이라는 정확성 제약이기도 하다 | `HangeulCompositionState.repeatDelete` |
| 반복 타이머 간격은 `max(0.01, 0.10 - repeatRate)`다 | 하한 10ms. 설정값이 아무리 커도 tick이 프레임보다 빨라지지 않는다 | `KeyboardTextInteractionPolicy.repeatTimerInterval` |
| 이전 삭제가 확정되기 전에는 다음 삭제를 보내지 않는다 | 빠른 반복 삭제가 호스트 반영 속도를 앞지르는 것을 막는다. 성능보다 정확성 결정이지만 tick 처리량의 상한이 된다 | `DeleteInteractionCoordinator` |
| 마침표 단축 상태 갱신은 정책이 문맥을 실제로 볼 때만 프록시를 읽는다 | 삭제 tick마다 `documentContextBeforeInput` 왕복을 줄인다 | `handlePeriodShortcutOnDelete()`, `KeyboardPeriodShortcutPolicy.requiresDocumentContextAfterDelete` |

### 2-5. 후보 바 표시

| 결정 | 이유 | 위치 |
|---|---|---|
| 후보 버튼과 divider는 재사용 풀이다 | 후보 개수가 바뀔 때 뷰를 만들지 않는다. 풀은 늘리기만 하고 줄이지 않는다 | `SuggestionBarView.ensurePooledViews` |
| 레이아웃 비용은 후보 개수를 메타데이터로 실어 잰다 | 3개 빌드와 10개 빌드를 따로 녹화하면 입력 타이밍과 학습 이력이 달라 비교가 안 된다. 한 녹화 안에서 개수별로 갈라 본다(§3-2) | `LayoutSuggestionContent` 구간의 `count=` |
| `delaysContentTouches = false` | 키보드에서 `UIScrollView` 기본 150ms 터치 지연은 쓸 수 없다 | `SuggestionBarView` |
| iOS 26 `UIScrollEdgeEffect`는 네 방향 모두 끄고, `CAGradientLayer` mask 페이드는 두지 않는다 | 가장자리 효과는 후보를 덮어 글자가 뭉개지고, mask는 매 프레임 offscreen 렌더링을 강제해 입력 경로에서 그냥 비용이다. 정위치에서는 페이드 영역에 글자가 없어 아무것도 알리지 못한다 | `SuggestionBarView`, CLAUDE.md 자동완성 항목 |
| 지구본 버튼은 `needsInputModeSwitchKey`가 바뀔 때만 다시 설정한다 | 레이아웃 패스마다 action 재등록과 App Group 저장을 하지 않는다 | `BaseKeyboardViewController.viewWillLayoutSubviews`, `appliedNeedsInputModeSwitchKey` |
| 후보 바 숨김이 바뀔 때만 높이를 다시 계산하고 다음 런루프로 미룬다 | 필드 전환마다 호출되는 경로라 값이 같으면 아무것도 하지 않는다 | `updateSuggestionBarHidden()` |

### 2-6. 언어 전환 (한영 통합)

| 결정 | 이유 | 위치 |
|---|---|---|
| 엔진을 언어(TextChecker)·NGram 식별자별 딕셔너리로 캐시한다 | 언어를 바꿀 때마다 디스크를 다시 읽지 않는다(#46). 단독 키보드는 전환 시 이전 언어 NGram을 `saveToDisk()`로 보존하고 `engineGeneration`으로 이전 언어의 로드 콜백을 무효화한다 | `SuggestionController.textCheckerEngines`, `nGramEngines`, `updateLanguage(to:)` |
| 한영 통합 키보드는 NGram 엔진이 하나(`"ko-en"`)다 | 전환 시 엔진을 건드리지 않고 문장 버퍼도 유지한다. NGram 후보를 보이는 중이면 새 언어의 선호 문자 종류로 다시 조회하되 순서가 달라졌을 때만 전달한다 | [한영 통합 키보드 §5](한영%20통합%20키보드.md), `refreshNGramSuggestionsForLanguageModeChange` |
| 통합 파일의 `maxKeys`는 10000이다 | 언어별 5000 + 5000과 같은 용량·메모리 최대치다. 저장 1회 비용은 파일이 커진 만큼 약 두 배로 봤다(§3-3, Mac 측정) | `NGramPredictiveTextEngine.maxKeys(forLanguage:)` |
| `isSuspended`는 설정 플래그와 분리한다 | 필드 전환마다 `autocorrectionType`에 따라 토글되는데, 그때마다 엔진을 해제·재생성하면 NGram 디스크 로딩이 반복된다 | [자동완성 로직 §5-2](자동완성%20로직.md) |

### 2-7. 메모리

| 결정 | 이유 | 위치 |
|---|---|---|
| 메모리 경고 시 현재 언어가 아닌 엔진 캐시와 썸네일 캐시를 해제한다 | 디스크 재로드 비용보다 메모리 확보가 우선이다. 단독 키보드의 비활성 NGram 엔진은 전환 시점에 이미 저장돼 있어 유실이 없다 | `BaseKeyboardViewController.didReceiveMemoryWarning`, `SuggestionController.releaseInactiveLanguageEngines()`, `ClipboardHistoryPanelView.purgeThumbnailCache()` |
| 자동완성을 끄면 TextChecker·NGram 엔진을 해제하고, 텍스트 대치까지 꺼지면 lexicon 엔진도 해제한다 | 쓰지 않는 엔진을 들고 있지 않는다 | `SuggestionController.isPredictiveTextEnabled`, `isTextReplacementEnabled` |
| NGram 키당 항목은 24개, 전체 키는 식별자별 5000개(통합 10000개)다 | 실제로 노출하는 후보는 10개뿐이고 나머지는 순위 변동용 빈도다. 키당 50 → 24개로 줄여 언어당 최악 메모리를 약 16.9MB에서 8.8MB로 낮췄다(2026-08-26, #46, 계산값) | `maxEntriesPerKey`, `maxKeys(forLanguage:)` |
| 클립보드 이미지는 원본을 통째로 디코드하지 않는다 | 파일 크기(24MB)와 헤더의 픽셀 수(50MP)로 저장 여부를 정하고, 예상 디코드 메모리가 키보드 예산(32MB)을 넘으면 건너뛴다(앱이 256MB 예산으로 대신 저장). 표시는 ImageIO 축소 디코드로 썸네일 240px·미리보기 1200px만 만든다. 원본 파일은 힙에 올리지 않고 rename만 하며, 해시는 64KB 스트리밍이다 | `ClipboardImagePolicy`, `ClipboardImageStore` |
| 썸네일은 `NSCache`(40개)에 두고 패널을 닫으면 미리보기를 놓는다 | 미리보기 디코드는 최대 약 5.8MB다 | `ClipboardHistoryPanelView.thumbnailCache`, `hideDetail` |
| 클립보드 텍스트 기록은 캐시 없이 매 연산 main에서 파일을 읽고 쓴다 | 세 extension이 같은 파일을 공유해 캐시가 있으면 다른 extension의 변경을 놓친다. 최대 40개 × 10,000자, 바이너리 plist 최악 약 800KB라 동기 처리로 충분하다고 봤다. 한도를 올리면 캐시 + 백그라운드 저장으로 바꾼다 | `ClipboardHistoryStore` (`ponytail:` 주석) |

`// ponytail:` 주석은 성능 한계와 개선 경로를 적어 둔 곳이다. 현재 4곳이다.

| 위치 | 한계 | 바꿀 조건 |
|---|---|---|
| `NGramPredictiveTextEngine.completions` | 키 입력마다 unigram 전체(최대 10000개)를 훑는다 | 남은 비용은 실제로 맞는 단어 몫이라 첫 자모 색인으로는 줄지 않는다. 저장 구조를 바꿀 때 별도 작업으로 |
| `ClipboardHistoryStore` | 매 연산 파일 I/O | 항목 수·길이 한도를 올리면 캐시 + 백그라운드 저장 |
| `ClipboardImagePolicy.heicScaledDecodeMaxPixelCount` | 24MP 이하 HEIC만 축소 디코드로 가정 | 실기기에서 48MP HEIC 썸네일 생성 메모리를 계측하면 올리거나 없앤다 |
| `ClipboardImagePolicy.keyboardDecodeMemoryBudget` | 디코드 예산 32MB 고정값 | 실기기 계측에서 이 예산의 디코드가 키보드를 종료시키면 낮춘다 |

## 3. 기준값과 측정 기록

측정값은 모두 기록에 있는 값이다. 표마다 날짜·기기·OS·빌드·데이터 조건을 적었다. 시뮬레이터와 Mac 값은
비교용이며 실기기 값과 직접 비교하지 않는다.

### 3-1. NGram 입력 중 단어 완성 (#158)

**기준: 실기기(iPhone 15 Pro Max, Release, 학습 단어 상한 10000개)에서 `NGramCompletions` p95 ≤ 4ms.**

- 120Hz 한 프레임(8.3ms)의 절반이다. 나머지 절반은 같은 키 입력의 조합·프록시 입력·후보 바 갱신 몫이다.
- 가장 느린 지원 기기(iOS 16, iPhone 8/A11)는 한 코어 성능이 약 2~3배 낮다고 보면(추정, 측정 아님) 8~12ms로
  60Hz 한 프레임(16.7ms) 안에 든다. 키 반응이 한 프레임 이상 밀리지 않는 것을 체감 기준으로 삼는다.
- 처음에는 "시뮬레이터 p95 2ms"였다. 체감과 연결된 근거가 없어 2026-09-26에 사용자 확인 뒤 바꿨다.

실기기 측정 흐름(iPhone 15 Pro Max / iOS 27.0, Release, `HangeulEnglishKeyboard.appex`, unigram 10000개,
2026-09-26). 한글 위주 데이터는 첫 음절을 '가·다·하·사·아·나'에 몰고 대문자 단어를 섞은 것, 영어 위주 데이터는
영어 9800개('s'로 시작 1106개) + 한글 300개다.

| 단계 | 데이터 | n | 중앙값 | p95 | 최대 |
|---|---|---:|---:|---:|---:|
| 처음 구현 | 한글 위주 | 138 | 4.52ms | 9.95ms | 11.55ms |
| 1차: 첫 스칼라 사전 거르기 | 한글 위주 | 167 | 0.93ms | 4.48ms | 5.04ms |
| 2차: 단순 스칼라 판정 + 대소문자 없는 단어 묶기 생략 | 한글 위주 | 151 | 0.73ms | 1.17ms | 1.23ms |
| 같은 코드 | 영어 위주 | 58 | 0.90ms | 3.76ms | 3.95ms |
| 3차: 표기 하나인 묶음 사전 생략 + bigram 없을 때 중복 검사 생략 | 영어 위주 | 55 | 0.80ms | 2.99ms | 3.09ms |

- 원인(Time Profiler, Mac M3 Pro에서 production 엔진·정책 소스를 `swiftc -O`로 묶은 벤치마크): 시간의 88%가
  `isCompletion`이고 그 안에서 `lowercased()` 28%, 글자 단위 `hasPrefix` 20%, 첫 자모 계산 13%, 글자 꺼내기 약 17%.
  맞는 단어 수보다 "1만 개 전부에 드는 고정 비용"이 컸다. 영어 데이터에서는 표기 묶기가 약 60%였다.
- 2차 조치 뒤 남은 중앙값은 1만 개를 한 번 훑는 바닥 비용이다(Mac에서 입력과 관계없이 약 0.11ms).
- 시뮬레이터(iPhone 13 mini / iOS 18.6, `-O`, 무작위 unigram 10000개, 2026-09-25) 처음 구현 값은 중앙값 0.84ms,
  p95 1.72ms, 최대 2.53ms였다. 무작위 데이터라 첫 음절이 흩어져 맞는 단어가 적었고, 실기기보다 낮게 나왔다.
  **시뮬레이터 값으로 기준 통과를 판단하지 않는다.**
- 모든 조치는 결과를 바꾸지 않았다. 이전 엔진과 나란히 돌려 완성 결과 38368건, 판정 약 157만 건에서 차이 0건을
  확인했다(§6-4).

### 3-2. TextChecker와 후보 바 (#123, #141)

**#123 자동완성 키 입력 경로**(iPhone 15 Pro Max / iOS 27.0, `HangeulEnglishKeyboard`, **Debug 빌드**, 애국가 1절 +
a~z 반복 + 개행·스페이스 연타). 당시 후보 상한은 3개였다.

| 구간 | 기준선 2026-09-02 (n / p50 / p95 / max) | 적용 후 2026-09-08 (n / p50 / p95 / max) | 적용 후 main 호출 |
|---|---|---|---|
| `TextCheckerSuggestions` | 69 / 11.93 / 17.08 / 21.92ms | 75 / 7.67 / 15.32 / 22.89ms | 0 / 75 (전부 전용 큐) |
| `TextCheckerGuesses` | 69 / 5.98 / 10.90 / 12.35ms | 7 / 11.37 / 15.43 / 16.60ms | 0 |
| `NGramSaveEncode` | 24 / 9.72 / 11.93 / 12.03ms | 9 / 9.60 / 12.56 / 13.73ms | 0 |
| `LexiconSuggestions` | 69 / 0.08 / 0.11 / 0.21ms | 75 / 0.01 / 0.03 / 0.04ms | 75 |
| `RankedUnigramCandidates` | 57 / 0.04 / 0.06 / 0.08ms | 35 / 0.02 / 0.03 / 0.13ms | 35 |

- 기준선 열은 2026-09-08에 같은 파서로 다시 계산한 값이라 2026-09-02 기록의 p95(17.37 / 11.16 / 11.97ms)와 소수점에서 다르다(보간 방식 차이).
- 지원 기기 중 최상위급에서도 TextChecker가 main을 12~22ms 점유했다. 이 값이 "한 프레임보다 오래 걸린다"는 근거다.
- 적용 후 키 입력당 main 점유는 0.05ms 미만(lexicon + 텍스트 대치 + unigram 합)이 됐다. TextChecker 자체 비용은
  그대로지만 전용 큐에서 소비된다. `guesses` 호출은 69회 → 7회, 변경 없는 저장은 24회 → 9회로 줄었다.
- 유지 기준은 `TextCheckerSuggestions` p50 ≥ 3ms 또는 p95 ≥ 8ms였다. 기준선이 두 배 이상 넘어 비동기 경로를
  실험이 아니라 핵심 개선으로 진행했다.

**#141 후보 상한 3 → 10 확장**(iPhone 15 Pro Max / iOS 27.0, `HangeulKeyboard.appex`, **Release**, 2026-09-21,
애국가 2행 + ㄱ 길게 + 삭제 길게, 24.3초).

| 후보 수 | n | `LayoutSuggestionContent` 평균 | 최대 |
|---:|---:|---:|---:|
| 1 | 10 | 1.203ms | 1.764ms |
| 9 | 11 | 1.256ms | 1.594ms |
| 10 | 22 | 0.842ms | 1.215ms |

- 재배치가 일어난 구간(>0.5ms)만 추린 값이다. 비용은 Auto Layout 패스이고 개수에 비례하는 루프가 아니다. 후보가
  바뀌지 않은 나머지 205회는 0.009~0.036ms다.
- 한 타의 main thread 합계는 최악 약 1.8ms로 60Hz 프레임 예산의 10% 수준이었다.
- 같은 녹화에서 `TextCheckerSuggestions` 69회는 평균 12.8ms, p95 33.7ms, 최대 125.4ms였다. 전부 전용 큐다.
  `UITextChecker.completions`는 개수 상한 인자를 받지 않아 상한과 무관하다.

### 3-3. NGram 기록·저장과 통합 파일 (#157)

모두 **시뮬레이터(iPhone 13 mini / iOS 18.6, Apple M3 Pro, `-O`)** 또는 Mac 측정이다. 실기기 로드 시간·메모리 기록은
없다. 실기기는 1.5~3배로 추정했다(측정 아님).

- Mac(M3 Pro, `swiftc -O`, 최악 크기 통합 파일 약 2.4MB): 로드 약 585ms, 인코딩·쓰기 약 550ms. 언어별 파일(약 1.2MB)은
  로드 약 335ms, 쓰기 약 275ms. 로드 시 메모리 증가 약 25MB(`ru_maxrss`).
- 시뮬레이터 production 엔진(2026-09-25, 0.2초 간격 150단어, 12단어마다 `endSentence()`) 스페이스 1회
  (중앙값 / p95 / 최대), `pruneKeys` 수정 전 → 후:

| 시나리오 | 수정 전 | 수정 후 |
|---|---|---|
| 통합 최악(키 10000개 가득) | 4.5 / 16.1 / 17.6ms, 16ms 초과 9회 | 1.9 / 12.3 / 15.3ms, 0회 |
| 통합 많은 사용(1년 × 하루 1,000단어) | 5.5 / 10.6 / 11.3ms | 3.3 / 6.4 / 7.0ms |
| 언어별 최악 | 3.2 / 7.5 / 8.9ms | 2.2 / 6.0 / 6.8ms |
| 언어별 많은 사용 | 2.6 / 5.3 / 5.8ms | 1.4 / 3.4 / 3.9ms |

- 스페이스 1회는 `addWord` + 문맥 후보 조회 + 빈 입력 후보 조회이고, `addWord` 시간의 약 98%가 `pruneKeys`(trigram 59~74%, bigram 24~40%)였다. copy-on-write 복사는 0.1~0.35ms로
  원인이 아니었다.
- 남은 p95는 새 문맥이 생길 때마다 키 전체의 빈도 합을 한 번 훑는 비용이다.
- 통합 최악 로딩(백그라운드)은 620~690ms, 로딩 뒤 유지 메모리 +21.3MB, 입력·저장 중 peak +41.8MB였다
  (테스트 호스트 앱 안의 증가량이며 extension 절대 메모리는 재지 않았다).

### 3-4. 삭제 가능 후보 굵기 표시 (#156, 하지 않은 것)

시뮬레이터(iPhone 13 mini / iOS 18.6, 2026-09-24). 삭제 가능한 후보를 medium 굵기로 표시하려고 후보마다
`UITextChecker.hasLearnedWord`를 불렀더니, 입력 중 글자마다 main thread에서 최대 18번 호출되고 학습 단어 수에
비례해 느려졌다. 학습 단어 100개면 글자당 약 4ms, 1000개면 약 63ms였다. 빌드 구성은 기록에 없다.
이슈를 닫았다(§4).

## 4. 하지 않기로 한 것

| 무엇 | 이유 | 다시 볼 조건 |
|---|---|---|
| 삭제 가능 후보를 medium 굵기로 표시(#156) | `hasLearnedWord`가 학습 단어 수에 비례해 느리고 글자마다 최대 18번 불린다(§3-4). 추천 단어 삭제는 온보딩 바텀시트에서 안내한다 | 학습 단어 목록을 엔진이 직접 들고 있어 O(1)로 판정할 수 있을 때 |
| NGram 학습 상한 줄이기(#158) | 다음 단어 예측 품질이 떨어지고, 기존 데이터를 지워야 하며, 새 단어를 못 배우는 상태가 빨리 온다(#158 작업 중 결정. 설계 문서에는 "범위 밖"만 있다) | 검토하지 않는다. 비용은 사전 거르기로 지킨다 |
| 첫 자모 색인·소문자 키 캐시(#158) | 학습 데이터와 어긋날 위험이 있다(#158 작업 중 결정). 남은 비용이 실제로 맞는 단어 몫이라 효과도 작다(설계 문서 §5) | 접두어 색인 등 저장 구조를 바꾸는 별도 작업에서 |
| 표기 묶음 사전 용량 미리 잡기(#158) | Mac에서 영어 's'가 0.376ms → 0.342ms로 줄었지만, 크기(1024)에 근거가 없고 맞는 단어가 적어도 키 입력마다 큰 사전을 잡는다 | 검토하지 않는다 |
| `PropertyListSerialization`으로 저장 형식 전환(#157) | Mac에서 쓰기 550 → 195ms, 읽기 585 → 293ms로 빠르지만 최대 메모리가 쓰기 +18 → +74MB, 읽기 +25 → +39MB로 늘었다. 문자열 약 24만 개를 `NSString`으로 새로 만들기 때문이다. 10단어마다 저장하는 extension에서 종료 위험이 속도 이득보다 크다 | 검토하지 않는다 |
| 상한 초과분을 모았다가 한 번에 정리(#157) | 상한을 잠시 넘게 되어 기존 동작이 바뀐다 | 실기기에서 스페이스 지연이 체감될 때 따로 |
| 한영 통합에서 ko/en 파일에 동시 기록(#157) | 분류 규칙, 삭제 동기화, 프로세스 간 덮어쓰기 비용 | 검토하지 않는다 |
| 후보 바 가장자리 페이드(#141) | `CAGradientLayer` mask가 매 프레임 offscreen 렌더링을 강제하고, 정위치에서는 알릴 내용이 없다 | 검토하지 않는다 |
| 후보 상한 3개와 10개를 따로 빌드해 비교 녹화(#141) | 입력 타이밍과 학습 이력이 달라 원인을 분리할 수 없다 | 한 녹화 안에서 메타데이터로 가른다(§6-1) |
| 클립보드 기록 메모리 캐시 | 세 extension이 파일을 공유해 캐시가 다른 extension의 변경을 놓친다 | 항목 수·길이 한도를 올릴 때 |
| 리뷰 팝업 지연 수정(#119) | `Task.sleep` 1초는 suspend라 입력을 막지 않아 원인이 아니다(#119 댓글). 남은 후보(StoreKit이 프롬프트 window를 올리고 App Store 연결을 기다리는 구간, 시뮬레이터 관측이면 호스트 CPU 포화)는 확정하지 못했다. 사람이 화면 녹화로 잴 항목이라 수치도 없다 | 원인을 실험으로 확정한 뒤 |

## 5. 새 기능을 넣을 때 확인할 것

- [ ] 키 입력마다 main thread에서 도는 코드가 늘어나는가? 늘어나면 `OSSignposter` 구간을 먼저 두고 실기기 Release로
      잰다. 기준은 §3-1과 같은 방식으로 프레임 예산에서 끌어낸다(부가 기능 하나는 120Hz 프레임의 절반 4ms).
- [ ] 학습 데이터·이력·후보 개수처럼 사용할수록 커지는 것을 훑는가? 상한이 있는가? 상한을 넘는 정상 경로가
      전체 정렬을 하지는 않는가?
- [ ] `UITextChecker`, 파일 I/O, `requestSupplementaryLexicon`처럼 한 프레임을 넘을 수 있는 호출을 main에서 동기로
      부르지 않는가? 큐로 보냈다면 세대 검사로 낡은 결과를 버리는가?
- [ ] 후보 갱신마다 시스템 API를 후보 수만큼 부르지 않는가? (#156의 `hasLearnedWord`가 그 예다)
- [ ] 필드 전환·`isSuspended`·언어 전환처럼 자주 바뀌는 상태에서 엔진이나 뷰를 재생성하지 않는가?
- [ ] 최적화가 결과를 바꾸지 않는가? 이전 코드와 나란히 비교했는가? 버그를 심어 테스트가 잡는지 확인했는가?
- [ ] 시뮬레이터나 Mac 값으로 기준 통과를 판단하고 있지 않은가? 실기기 값이 시뮬레이터보다 몇 배 높게 나온 적이
      있다(§3-1: 시뮬레이터 p95 1.72ms, 실기기 9.95ms).
- [ ] 메모리를 더 쓰는가? 메모리 경고 시 놓을 수 있는가? 이미지라면 디코드 예산 안인가?
- [ ] 다른 extension과 공유하는 파일에 캐시를 두고 있지 않은가?
- [ ] 의도적으로 남긴 한계에 `// ponytail:` 주석으로 한계와 바꿀 조건을 적었는가?
- [ ] 측정 결과를 기기·OS·빌드·데이터·날짜와 함께 기록했는가? 측정하지 않은 값을 추정이라고 표시했는가?

## 6. 측정 방법

### 6-1. signpost 추가

- category별 `OSSignposter`가 이미 있다: `KeyboardLifecycle`(VC), `SuggestionController`, `NGramPredictiveTextEngine`,
  `TextCheckerPredictiveTextEngine`, `SuggestionBarView`. 구간 목록은 [자동완성 로직 §12](자동완성%20로직.md)에 있다.
- 구간 이름은 무엇을 재는지 드러나게 짓고, main에서 도는지 큐에서 도는지 문서에 적는다.
- 같은 이름의 구간이 중첩되거나(`TextCheckerSuggestions` 안의 `TextCheckerCompletions`) 스레드를 걸치는 경우
  (`NGramBackgroundLoad`는 global 큐에서 시작해 main에서 끝나므로 main 큐 대기가 포함된다)는 판독 때 주의한다.
- 한 녹화 안에서 조건별로 가르려면 메타데이터를 싣는다(`LayoutSuggestionContent`의 `count=`).

### 6-2. 실기기 Instruments 기록과 판독

1. Instruments에서 Blank 템플릿에 os_signpost 계측기를 추가하고, 대상 프로세스를 키보드 확장
   (예: `HangeulEnglishKeyboard.appex`)으로 한정한다. Release 빌드로 기록한다. Debug 빌드 값은 Release와 다르다(§3-2).
2. 입력 스크립트를 정해 두고 같은 순서로 입력한다. 이전 측정과 비교하려면 같은 데이터·같은 입력이어야 한다.
3. trace를 XML로 뽑는다.

```sh
xcrun xctrace export --input <trace> --toc
xcrun xctrace export --input <trace> \
  --xpath '/trace-toc/run[@number="1"]/data/table[@schema="os-signpost"]' \
  --output signposts.xml
```

4. Begin/End를 **(이름, identifier) 쌍**으로 짝지어 구간 길이를 계산하고 이름별로 n / 중앙값 / p95 / 최대를 낸다.
   identifier만으로 맞추면 `OS_SIGNPOST_ID_EXCLUSIVE`라 중첩 구간이 뒤섞인다. thread는 짝짓기 키에 넣지 않는다.
   같은 이름의 구간이 다른 스레드에서 겹치는 경우가 지금 코드에는 없고, `NGramBackgroundLoad`처럼 스레드를 걸치는
   구간은 thread까지 맞추면 짝이 안 맞아 결과에서 빠진다. xctrace XML은 반복 값을 `ref="id"`로
   가리키므로 파서가 id를 해석해야 한다. 계산 스크립트는 저장소에 두지 않고 임시 폴더에서 쓴다.
5. Instruments가 `log/signpost messages lost due to high rates` 경고를 내면 그 구간은 비교에서 뺀다.

### 6-3. 실기기 학습 데이터 교체

상한(10000개)에 가까운 데이터로 재려면 기기 App Group의 NGram 파일을 바꾼다.

```sh
# 기기 파일 백업
xcrun devicectl device copy from --device <UDID> \
  --domain-type appGroupDataContainer --domain-identifier group.github.com-SNMac.SYKeyboard \
  --source 'Library/Application Support/ngram_ko-en.plist' --destination ./backup/ngram_ko-en.plist
# 측정용 파일로 교체
xcrun devicectl device copy to --device <UDID> \
  --domain-type appGroupDataContainer --domain-identifier group.github.com-SNMac.SYKeyboard \
  --source ./ngram10000.plist --destination 'Library/Application Support/ngram_ko-en.plist'
```

- 옵션 이름은 `xcrun devicectl device copy to --help` 기준이다. #158 측정 때 실제로 쓴 명령은 임시 폴더에만 있었으므로 실행 전에 `--help`로 다시 확인한다.
- 교체 전후에 키보드 확장 프로세스를 종료한다(키보드를 내리고 호스트 앱을 종료). 살아 있는 프로세스가 이전 데이터를
  다시 저장해 덮어쓴다.
- 측정이 끝나면 백업으로 복원한다. 한글 위주·영어 위주처럼 데이터 특성이 결과를 바꾸므로(§3-1) 데이터 구성을 기록한다.

### 6-4. 결과 불변 확인과 Mac 벤치마크

- **나란히 비교**: production 엔진·정책 소스와 `git show <이전 커밋>:<경로>`로 꺼낸 이전 코드를 한 실행 파일로
  `xcrun swiftc -O` 컴파일하고, 같은 데이터·같은 입력으로 둘을 불러 결과를 비교한다. 동률 순서 차이를 없애려면
  빈도를 겹치지 않는 무작위 값으로 바꾼 데이터를 쓴다.
- **변이 테스트**: 최적화 조건을 일부러 깨뜨린 변이(안전 범위 밖 스칼라도 거르기, 묶기를 늘 건너뛰기 등)에서 새
  테스트가 실패하는지 확인한 뒤 원래 코드로 되돌린다. 기존 테스트가 모두 통과하는 변이가 있으면 그 공백을 메우는
  테스트를 먼저 추가한다.
- **Time Profiler**: `xctrace record --template 'Time Profiler' --launch -- ./bench <데이터> <반복>`으로 원인을 찾는다.
  Mac 값은 상대 비교용이고, 실기기는 Mac의 약 5~7배로 나온 적이 있다(§3-1, 추정 근거일 뿐 환산 기준이 아니다).
  Mac 부하가 높으면 벽시계 대신 같은 프로세스에서 이전·새 코드를 번갈아 부르며 스레드 CPU 시간을 비교한다.
- **시뮬레이터 임시 테스트**: `SWIFT_OPTIMIZATION_LEVEL=-O -parallel-testing-enabled NO`로 돌리는 임시 성능 테스트는
  같은 명령 끝에서 지운다. 저장소에 성능 단언 테스트를 남기지 않는다.
