# 삭제와 실행취소 로직

삭제 확정 파이프라인(`DeleteMutationLifecycle` / `DeleteInteractionCoordinator`), 삭제 팬 제스처,
반복 삭제, undo/redo 시스템(`KeyboardUndoRedoSession`)을 정리한다.
관련 문서: [전체 아키텍처](전체%20아키텍처.md) · [한글 입력 로직](한글%20입력%20로직.md) · [자동완성 로직](자동완성%20로직.md)

---

## 1. 왜 "삭제 확정"이 필요한가

`textDocumentProxy` 편집은 호스트 앱에 비동기로 반영된다. 삭제 요청을 보냈다고 해서 실제로 지워졌다는
보장이 없고, 결과는 다음 `textDidChange(_:)`에서 문맥(`documentContextBeforeInput`/`AfterInput`)을 비교해야 알 수 있다.
그런데 다음 두 가지는 **실제로 지워졌을 때만** 일어나야 한다.

- **undo 기록**: 지워지지 않은 삭제를 기록하면 undo가 텍스트를 오염시킨다.
- **피드백**: 반복 삭제·팬 삭제의 햅틱/사운드는 실제 삭제에만 재생한다.

또한 빠른 반복 삭제는 호스트 반영 속도를 앞지를 수 있으므로, **이전 요청이 확정되기 전에는 다음 삭제를 보내지 않는다.**
이를 위해 삭제 요청을 "시작 → 편집 캡처 → 문맥 변경 확인 → 확정(resolve)"의 수명주기로 관리한다.

관련 타입은 모두 `Modules/SYKeyboardCore/Presentation/Utils/Policies/KeyboardTextInteractionPolicy.swift`에 있고,
Base VC가 두 인스턴스를 보유한다.

```
BaseKeyboardViewController
├── deleteMutationLifecycle: DeleteMutationLifecycle      ← 요청 1건의 수명주기 (시작→캡처→확정)
└── deleteInteractionCoordinator: DeleteInteractionCoordinator ← 요청 여러 건의 FIFO 직렬화 (generation 단위)
```

## 2. DeleteMutationLifecycle — 요청 수명주기

### 2-1. 요청 종류

| RequestKind | 시작 지점 | released 변형 |
|---|---|---|
| `touchDown` | 삭제 버튼 단일 탭 | `releasedTouchDown` — 버튼을 뗐지만 아직 미확정 |
| `repeatTick` | 반복 삭제 tick | `releasedRepeatTick` — 반복 종료 후 미확정 |
| `panBoundary` | 팬 삭제 중 개행 경계 추론 (§4-3) | `releasedPanBoundary` |

### 2-2. 흐름

```
begin{TouchDown,Repeat,PanBoundary}(context:selectedText:)   ← 요청 시작, 시작 문맥 스냅샷
    ↓
capture(deletedText:insertedText:reliability:)               ← 래핑 메서드가 수행한 편집을 draft로 캡처
    ↓                                                           (recordUndoRedoChange 경유, 여러 건 가능)
completeAfterTextChange(...)                                 ← textDidChange에서 문맥 비교로 확정
completeAtCheckpoint(...)                                    ← 또는 체크포인트(다음 tick, 버튼 뗌 등)에서 확정
    ↓
DeleteMutationResolution(completion:origin:shouldPlayFeedback:)
```

캡처된 draft(`RepeatDeleteMutationDraft`)는 신뢰도를 갖는다.

- `.authoritative`: 삭제된 텍스트를 확실히 아는 경우 (`selectedText` 삭제, `replaceText`의 문맥 suffix).
- `.proxyContext`: `documentContextBeforeInput` 마지막 글자로 추정한 경우 (일반 `deleteText`).

### 2-3. 확정 검증 (`RepeatDeleteRequest.confirmedDrafts`)

시작 문맥과 현재 문맥을 비교해 draft가 실제로 반영됐는지 검증한다.

- 선택 삭제 요청: draft 1건 + `.authoritative` + `deletedText == 시작 selectedText`일 때만 인정.
- `.authoritative` draft들: 시작 before-context에 draft를 순서대로 적용한 결과가 현재 before-context와 일치해야 인정.
- `.proxyContext` draft: `현재 before == 시작 before에서 deletedText를 뗀 것`이면 인정.
- **개행 추론**: before-context가 그대로인데 textDidChange가 왔거나(같은 줄 유지),
  빈 before에서 이전 줄 내용이 나타난 경우 → 실제로는 `"\n"`이 지워진 것으로 보고
  draft를 `deletedText: "\n"`(authoritative) 1건으로 대체한다.
  (proxy 문맥은 줄 단위라서 개행 삭제가 문맥상 안 보이는 경우가 있다.)

확정 결과는 `RepeatDeleteCompletion.mutations([draft])` 또는 `.noDeletion`이다.

### 2-4. Resolution 처리 (`processDeleteMutationResolution`)

```
1. panBoundary 확정이 "\n" 삭제였다면 tempDeletedCharacters에 "\n" 추가 (팬 복구용)
2. .mutations이면 draft들을 recordUndoRedoChange로 undo 세션에 기록
3. origin이 repeatTick/panBoundary이고 실제 삭제였으면 햅틱 + 삭제 사운드 재생
4. coordinator의 현재 generation을 resolve하고 보류 큐를 drain
```

## 3. DeleteInteractionCoordinator — 요청 직렬화

빠른 연타/팬 중에 들어오는 삭제 이벤트를 generation 단위 FIFO로 직렬화한다.

- `beginTouchDown(button:inputIdentifier:)`: 진행 중 generation이 없으면 `.performNow`,
  있으면 `.enqueued`로 큐에 쌓는다 (`PendingDeleteInteractionEvent.touchDown/pan/panStop`).
- 확정(resolve)되면 `nextReadyEvent()`로 보류 이벤트를 순서대로 꺼내 실행한다
  (`drainPendingDeleteInteractionsIfPossible`, 재진입은 `isDrainingPendingDeleteInteractions`로 차단).
- `cancelIfInputIdentifierChanged(to:)`: 텍스트 필드가 바뀌면 진행분·보류분을 모두 취소한다
  (`textWillChange`/`textDidChange`의 `synchronizeDeleteInteractionInputIdentifier`).
- 삭제가 아닌 다른 입력이 시작되면 `cancelPendingDeleteInteractions()`로 전체 취소한다.
- resolve 시 `discardingLeadingNoOpPanLeft`로, 아무것도 지우지 못한 팬 왼쪽 이벤트가 큐 앞에 쌓여 있으면 버린다.

## 4. 삭제 상호작용 3종

### 4-1. 단일 삭제 (touchDown)

삭제 버튼은 다른 버튼과 달리 **누르는 즉시** 입력을 수행한다.

```
touchDown → performTextInteraction(.deleteButton)
  1. 이전 releasedTouchDown 요청이 있으면 체크포인트로 확정 시도
  2. coordinator.beginTouchDown → 큐잉되면 종료
  3. lifecycle.beginTouchDown → 시작 문맥 스냅샷
  4. textInteractionWillPerform → 본문 → textInteractionDidPerform (semantic hooks)
     본문: 텍스트 대치 복구 시도 → 실패 시 deleteBackward()
           (한글 VC는 deleteBackward를 오버라이드해 자소 분해 수행)
touchUp → lifecycle.finishTouchDown
  확정 가능하면 즉시 resolve, 아니면 releasedTouchDown으로 전환해 textDidChange를 기다림
```

한글 VC는 `textInteractionWillPerform/DidPerform`에서 `beginDeleteTouchDown`/`endDeleteTouchDown` 스냅샷을 찍어
팬 복구 보정값을 준비한다 ([한글 입력 로직 §6](한글%20입력%20로직.md)).

### 4-2. 반복 삭제 (길게 누르기)

```
길게 누르기 → repeatTextInteractionWillPerform → (한글 VC) performInitialRepeatDeleteTextInteraction
  첫 tick은 조합 상태를 보존한 채 일반 삭제 경로로 수행하고 피드백도 실제 삭제 기준으로 재생

이후 타이머 tick마다 performRepeatDeleteTextInteraction:
  lifecycle.actionForNextRepeat(currentContext:currentSelectedText:)
  ├── .deleteAwaitingTextChange(이전 resolution) → 이전 tick 확정 처리 후 이번 tick 삭제 수행
  ├── .awaitingPreviousMutation                 → 이번 tick 건너뜀 (호스트 반영 대기)
  └── .finishWithoutDeletion                    → 더 지울 게 없음 → 반복 중단

반복 종료(repeatTextInteractionDidPerform):
  completeRepeatDeleteAtCurrentContext로 마지막 tick 확정 시도,
  미확정이면 released 상태로 textDidChange를 기다림 (stopRepeatInputTracking(preservingTouchDown:))
  (한글 VC) finishRepeatDelete로 committed 끌어오기 수행
```

즉 **체크포인트 방식**이다: 매 tick이 직전 tick의 확정을 겸하므로, textDidChange가 늦어도 반복이 이어지고
아무것도 안 지워지는 상황이 감지되면 스스로 멈춘다.

타이머 간격: `KeyboardTextInteractionPolicy.repeatTimerInterval(repeatRate:) = max(0.01, 0.10 - repeatRate)`
(기본 `repeatRate` 0.05 → 0.05초).

### 4-3. 삭제 팬 제스처 (드래그 삭제/복구)

`TextInteractionGestureController`가 `cursorMoveInterval`마다 `deleteButtonPanning(to: .left/.right)`를 보낸다.

```
왼쪽 팬 (삭제):
  coordinator.enqueuePan → 진행 중 요청 있으면 큐잉
  lifecycle.actionForDeletePan → 준비되면 performDeleteButtonPanInteraction(.left)
  ├── deleteButtonPanDeleteText(...) 성공  → 글자 단위 삭제, shouldRestore면 tempDeletedCharacters에 push,
  │                                          후보 갱신 + 햅틱/사운드 (lifecycle 요청 없이 즉시)
  └── nil (지울 문맥이 안 보임)           → shouldRequestDeletePanBoundary 판정:
                                             hasText인데 before-context와 selection이 비어 있으면
                                             개행 경계로 보고 beginPanBoundary(expectation: .newline) 후 deleteText()
                                             → 확정 시 "\n"이 tempDeletedCharacters에 들어가 복구 가능

오른쪽 팬 (복구):
  tempDeletedCharacters.popLast() → deleteButtonPanRestoreText(_:)
  (한글 VC는 조합 상태에 반영: 한글이면 composing 재개, 아니면 committed에 추가)

팬 종료:
  deleteButtonPanStopped → coordinator.enqueuePanStop
  → 확정 대기 중이면 finishPanBoundary/체크포인트 예약(scheduleReleasedPanBoundaryCheckpoint) 후
    tempDeletedCharacters 비우고 deleteButtonPanDidStop() (한글 VC: finishDeletePan)
```

임시 삭제 버퍼(`tempDeletedCharacters`)는 삭제 버튼 이외의 상호작용이 시작되면 비워진다
(`textInteractionWillPerform`).

## 5. Undo/Redo 시스템

파일: `Modules/SYKeyboardCore/Presentation/Utils/KeyboardUndoRedoManager.swift`

```
KeyboardUndoRedoSession                ← VC가 보유. 디바운스, 지연 확정, 필드 전환 무효화
└── KeyboardUndoRedoManager (struct)   ← undo/redo 스택 (최대 100), pending 그룹 병합
    └── KeyboardTextMutation           ← (deletedText, insertedText, 전후 문맥 스냅샷)
KeyboardTextContextSnapshot            ← (beforeInput, afterInput) 문맥 스냅샷
KeyboardTextContextNavigator           ← 두 스냅샷 사이 커서 offset 탐색 (최대 256자)
```

### 5-1. 활성 조건과 UI

```
isUndoRedoFeatureAvailable = isPredictiveTextEnabled && isUndoRedoEnabled
표시 조건 = 위 + SuggestionBar가 보임 (KeyboardPresentationStatePolicy.shouldShowUndoRedoControls)
```

undo/redo 버튼은 `SuggestionBarView` 우측에 있으며, 활성화 여부는 매번
`canApplyUndo/Redo(from: 현재 문맥)`으로 판정한다 (스택에 있어도 커서를 되돌릴 수 없으면 비활성).

### 5-2. 기록과 그룹 병합

모든 래핑 메서드(`insertText`/`deleteText`/`replaceText`)가 `recordUndoRedoChange(deletedText:insertedText:)`를 호출한다.
이 함수는 먼저 삭제 확정 파이프라인에 캡처를 시도하고(§2), 삭제 요청 중이 아니면 undo 세션에 기록한다.

`KeyboardUndoRedoManager.record`는 연속 편집을 하나의 `pendingMutation`으로 병합한다.

| 병합 규칙 | 예 |
|---|---|
| 삭제 + 삭제 | deletedText를 앞에 이어붙임 |
| 삽입 + 삽입 | insertedText를 뒤에 이어붙임 |
| 삽입 후 그 일부를 지우고 재삽입 (`insertedText.hasSuffix(other.deletedText)`) | 한글 조합의 delete→reinsert가 한 그룹으로 합쳐짐 (예: "ㅎ"→"하"→"한" 입력이 undo 1회 분량) |
| 재삽입분보다 더 크게 지운 경우 | 추가 삭제분을 deletedText로 흡수 |
| 방향 전환 (삽입↔삭제) | `shouldStartNewGroup` → 기존 그룹 확정 후 새 그룹 시작 |

### 5-3. 그룹 확정 시점

| 트리거 | 메서드 |
|---|---|
| 0.8초 입력 없음 (디바운스) | `scheduleDebounceCommit` |
| 스페이스/리턴 | `commitUndoRedoGroupIfPossible()` |
| 삭제 시작 | `commitUndoRedoGroupIgnoringCompositionDeferral()` — 조합 중이어도 이전 편집 단위를 끊음 |
| 조합 종료 | `commitDeferredUndoRedoGroupIfNeeded()` |

**조합 지연**: `shouldDeferUndoRedoCommit`(한글: `!composingBuffer.isEmpty`)이 `true`인 동안
디바운스 확정이 미뤄진다(`needsDeferredCommit`). 조합 중간 상태가 별도 undo 단위로 쪼개지는 것을 막는다.

### 5-4. 적용

```
performUndo/performRedo:
  1. 진행 중 삭제 확정 취소, 디바운스 취소
  2. canApplyUndo/Redo(from: 현재 문맥) 확인
  3. edit = session.undo()/redo()   ← KeyboardUndoRedoEdit(deleteCount, insertText, targetContext)
  4. restoreTextPositionIfPossible: KeyboardTextContextNavigator.cursorOffset으로
     현재 문맥 → 기록 시점 문맥의 커서 offset을 찾아 adjustTextPosition (최대 ±256자 탐색)
  5. deleteCount만큼 deleteBackward → insertText (proxy 직접 조작, isApplyingEdit 플래그로 재기록 방지)
  6. undoRedoEditDidApply(): inputBuffer 초기화 + 대치 이력 초기화
     (한글 VC: 조합 상태 리셋 + 스페이스/Shift 버튼 갱신)
  7. 반대 방향 target context 갱신, 컨트롤 갱신, 햅틱
```

### 5-5. 무효화

- **텍스트 필드 전환**: `textWillChange`에서 스냅샷을 준비하고, `textDidChange`에서
  `shouldInvalidateAfterTextChange`가 input 식별자 변경을 감지하면 스택 전체 제거 + 대치 이력 초기화.
- **적용 실패**: 커서 offset을 찾지 못하면(사용자가 다른 위치를 편집한 경우) 스택 제거.
- **키보드 사라짐**: `viewWillDisappear`에서 스택 제거 (세션 한정 기능).

이 시스템을 이해할 때 기억할 전제:

- 반복 삭제·팬 삭제의 햅틱/사운드는 요청 시점이 아니라 **실제 삭제 확정 시점**에 재생된다.
- 개행 경계 추론(§2-3, §4-3)은 proxy 문맥이 줄 단위라서 개행 삭제가 문맥 비교에 보이지 않는 제약에 대한 보정이다.
- 파이프라인 전체가 `textDidChange` 호출을 전제로 한다. `selectionDidChange`는 호출이 관찰되지 않아 사용하지 않는다.
