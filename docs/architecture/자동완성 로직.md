# 자동완성 로직

자동완성 후보, 다음 단어 예측(n-gram), 텍스트 대치/복구, 수식 결과 후보의 구조와 호출 시점을 정리한다.
관련 문서: [전체 아키텍처](전체%20아키텍처.md) · [한글 입력 로직](한글%20입력%20로직.md) · [삭제와 실행취소 로직](삭제와%20실행취소%20로직.md) · [한영 통합 키보드](한영%20통합%20키보드.md)

---

## 1. 전체 아키텍처

```
사용자 터치
    ↓
BaseKeyboardViewController                (버튼 이벤트 라우팅, inputBuffer 관리)
    ↓
SuggestionController (SuggestionService 프로토콜 구현)
    ├── LexiconPredictiveTextEngine       ← UILexicon (텍스트 대치, 정확 일치)
    ├── TextCheckerPredictiveTextEngine   ← UITextChecker (시스템 사전 + 오타 교정, 언어별 캐시)
    ├── NGramPredictiveTextEngine         ← 사용자 이력 (다음 단어 예측, NGram 식별자별 캐시)
    └── MathExpressionCompletionEvaluator ← 수식 평가 (엔진이 아닌 정적 evaluator)
    ↓ (SuggestionControllerDelegate)
SuggestionBarView
    ├── 클립보드 버튼                     ← 클립보드 기록 패널 토글 (후보와 별개, §10)
    ├── 후보 가로 스크롤 영역             ← 모드별 후보 표시 (3칸이 보이고 최대 10개, 넘치면 스크롤)
    └── undo/redo 버튼                    ← KeyboardUndoRedoSession 연동 (후보와 별개)
```

후보 버튼은 고정된 3개가 아니라 `UIScrollView` 안의 재사용 풀이다. 이 문서의 button1/button2/button3은
식별자가 아니라 앞에서부터 센 칸 위치(후보 인덱스 0/1/2)를 가리킨다.

핵심 원칙:

- **세 가지 표시 모드**(`SuggestionMode`)가 분리되어 동작한다: `.typing`(입력 중), `.nGram`(다음 단어 예측), `.mathExpression`(수식 결과).
- **엔진은 후보 생성만 담당하고, 텍스트 조작(삭제/삽입)은 VC가 전담**한다.
- **모든 후보 조회는 `inputBuffer` 기준**이다. `documentContextBeforeInput` 대신 현재 키보드 세션에서 직접 입력한
  텍스트만 사용해, 다른 키보드나 앱이 채운 텍스트가 학습·제안에 섞이는 것을 방지한다.
  한영 통합 키보드도 언어 경계로 나누지 않고 같은 `inputBuffer`를 그대로 쓴다. 단어 완성·대치/복구·수식
  판단·NGram 기록/조회/삭제 뒤 문장 버퍼 동기화 모두 단일 언어 키보드와 같은 경로다
  ([한영 통합 키보드 §4](한영%20통합%20키보드.md)).
- **엔진 생성은 지연**된다. `viewDidLoad`에서는 설정만 전달하고, 첫 표시 이후 준비 API에서 생성한다.
- **학습 정책은 출처별로 다르다**: textChecker 후보만 `UITextChecker.learnWord`로 학습한다.

주요 파일 (모두 `Modules/SYKeyboardCore/`):

| 파일 | 역할 |
|---|---|
| `Domain/Protocols/SuggestionService.swift` | 서비스 프로토콜 + `MathResultSuggestionAction` |
| `Domain/SuggestionController.swift` | 기본 구현. 엔진 병합, 모드 관리, 대치/복구, 식별자별 엔진 캐시(textChecker는 언어별, n-gram은 언어 코드 또는 통합 식별자별) |
| `Domain/PredictiveText/*.swift` | 세 예측 엔진 (`Protocols/PredictiveTextProvider.swift`에 프로토콜) |
| `Domain/MathExpressionCompletionEvaluator.swift` | 수식 후보 평가기(파서 포함) |
| `Presentation/View/SuggestionBarView.swift` | 후보 바 UI, 터치/하이라이트, 클립보드·undo/redo 버튼 |
| `Presentation/Utils/Policies/KeyboardSuggestionSelectionPolicy.swift` | 후보 갱신 대상/수식 탐지 텍스트 결정, n-gram 후보 앞 공백 규칙, 현재 단어 확정 대상, lexicon 로드 시점, 후보 삭제 길게 누르기 시간 |
| `Presentation/Utils/Policies/SuggestionHighlightPolicy.swift` | 하이라이트 우선순위(터치 > preview)와 후보 divider 개수 규칙(`SuggestionDividerPolicy`) |
| `Presentation/Utils/Policies/PredictiveTextScriptPolicy.swift` | NGram 후보 단어의 문자 종류(한글/라틴/기타) 판별, 언어 모드별 선호 문자 종류 |

## 2. 핵심 엔진 구조

세 엔진 모두 `PredictiveTextProvider`를 채택한다.

```swift
protocol PredictiveTextProvider: AnyObject {
    func suggestions(for baseText: String) -> [String]
    func suggestions(for baseText: String, limit: Int) -> [String]  // 기본 구현은 suggestions(for:) 그대로
    func learn(word: String)
    func canUnlearn(word: String) -> Bool   // 기본 구현은 false
    func unlearn(word: String)              // 기본 구현은 no-op
}
```

`limit`은 호출자가 실제로 읽는 최대 개수다. 후보 생성 비용이 큰 textChecker 엔진만 재정의해 limit을 채우면 조회를 멈춘다.
`canUnlearn`/`unlearn`은 후보를 길게 눌러 삭제할 때 쓰며(§6-1) textChecker 엔진만 재정의한다.

### 2-1. LexiconPredictiveTextEngine

`UILexicon` 기반. 연락처·텍스트 대치 항목 등 개인화 데이터를 사용한다.

| 항목 | 내용 |
|---|---|
| 프로토콜 | `LexiconSuggestionProviding`(+ 로딩용 `LexiconLoadableSuggestionProviding`) |
| 데이터 소스 | `UILexicon` (시스템 관리, `requestSupplementaryLexicon`으로 로드) |
| 매칭 | 현재 단어와 `entry.userInput`이 **정확히 일치**(lowercased)할 때만 `documentText` 반환 |
| 대치 항목 노출 | `textReplacementEntries(matching:)` — `setLexicon`에서 만든 `userInput.lowercased()` 인덱스 조회 (대치 매칭은 컨트롤러가 수행) |
| 학습 | 불필요 (`learn`은 빈 구현) |
| 예외 | iOS 버그 대응으로 `'m' → 'M'` 항목은 대치 매칭에서 제외 (`SuggestionController.textReplacementMatch`의 필터) |

```
입력: "ㅈㄱㅈ", lexicon에 userInput="ㅈㄱㅈ", documentText="지금 가는 중!" 존재
→ ["지금 가는 중!"] 반환
```

### 2-2. TextCheckerPredictiveTextEngine

`UITextChecker` 기반. 생성 시 언어 코드(`"ko-KR"` / `"en-US"`)를 받는다.

| 항목 | 내용 |
|---|---|
| 매칭 | 1순위 `completions`(접두어 자동완성) → 2순위 `guesses`(오타 교정), lowercased 기준 중복 제거 후 순차 병합. `suggestions(for:limit:)`로 limit을 받고, completions만으로 limit이 차면 guesses를 호출하지 않는다 |
| 스레드 | `checker` 인스턴스는 `SuggestionController`의 TextChecker 큐에서만 접근한다. `learn(word:)`의 `UITextChecker` 클래스 메서드는 main에서 호출 |
| 학습 | `learn(word:)` → `UITextChecker.learnWord` + 학습 목록 저장. `hasLearnedWord`로 중복 학습 방지 |
| 학습 목록 저장소 | App Group `UserDefaults` 키 `com.snmac.sykeyboard.textchecker.learnedWords` (일괄 초기화용) |
| 초기화 | `unlearnAllWords()` — 메인 앱 설정 화면에서 사용 |
| 단어 단위 해제 | `canUnlearn(word:)` = `UITextChecker.hasLearnedWord`, `unlearn(word:)` → `UITextChecker.unlearnWord` + 학습 목록에서 제거 (§6-1) |

```
completions: "hel"  → ["hello", "help", "helmet", ...]
guesses:     "helo" → ["hello", "hero", ...]
```

### 2-3. NGramPredictiveTextEngine

사용자 입력 이력 기반 다음 단어 예측. NGram 식별자별로 데이터가 분리된다. 한글/영문 키보드는
식별자가 `language`(예: `"ko-KR"`, `"en-US"`)와 같고, 한영 통합 키보드는 두 언어가
`NGramPredictiveTextEngine.hangeulEnglishLanguage`(`"ko-en"`) 하나를 공유한다.

| 항목 | 내용 |
|---|---|
| 저장소 | App Group 컨테이너의 `Library/Application Support/ngram_{식별자}.plist` (바이너리 plist, 예: `ngram_ko-KR.plist`, `ngram_ko-en.plist`). 컨테이너 루트에 있던 옛 파일은 생성 시 `moveLegacyFileIfNeeded`로 한 번 옮기고, 옮기지 못하면 옛 파일을 계속 읽되 저장은 새 위치로 한다 |
| 조회 | 1순위 trigram(직전 2단어) → 2순위 bigram(직전 1단어) → 3순위 unigram(빈도순 보충). 문맥이 없으면 unigram만.
  `suggestions(for:preferredScript:)`에 `preferredScript`(`PredictiveTextScriptPolicy`가 정한 문자 종류)를 주면
  unigram 후보만 그 문자 종류 상위 후보를 먼저, 나머지를 뒤에 둔다(trigram/bigram은 문자 종류와 무관하게 빈도순).
  unigram 순위는 `preferredScript`별로 `rankedUnigramCache`에 캐시하고 unigram이 바뀔 때 무효화 |
| 기록 | `addWord(_:)`가 문장 버퍼(`currentSentenceWords`)에 쌓으며 unigram/bigram/trigram 동시 기록 |
| 단어 삭제 | `removeWord(_:)` — 후보 길게 눌러 삭제 시 호출 (§6-1) |
| 상한 | 키당 최대 **24개** 항목(`maxEntriesPerKey`, 빈도 낮은 것부터 정리), 전체 최대 키 수(`maxKeys`)는 식별자별
  5000개, 한영 통합(`"ko-en"`)만 10000개(두 언어가 한 파일을 나눠 쓰므로 단독 키보드 두 엔진분 용량에 맞춘다).
  상한을 넘으면 unigram은 빈도, bigram·trigram 키(`pruneKeys`)는 총 빈도가 가장 낮은 것부터 지운다. 기록마다 1개만
  넘는 정상 경로는 전체 정렬 없이 최솟값 1개만 찾는다(가득 찬 저장소에서는 trigram 새 문맥이 거의 매 스페이스마다 생긴다) |
| 디스크 저장 | 10회 기록마다(`writePeriod`) + `endSentence()` + `saveNGramData()`(키보드 사라질 때). 메인 스레드 스냅샷 → `.utility` 직렬 큐에서 인코딩·쓰기. 마지막 저장 이후 변경이 없으면(`hasUnsavedChanges`) 건너뛴다. 보류된 레거시 정리만 예외 |
| 비동기 로딩 | `init`에서 백그라운드 로드. 완료 전 조회는 빈 배열, **기록은 버리지 않고 `pendingEvents`에 쌓았다가 로드 후 순서대로 재생** |
| 로드 완료 통지 | `onLoadCompleted` 콜백 → 컨트롤러가 마지막 요청 기준으로 후보를 재갱신 |
| 경합 방지 | `storageGeneration`으로 reset과 비동기 load/save 결과를 구분 |
| 마이그레이션 | 레거시 `UserDefaults` 키 발견 시 파일로 이전 후 제거 (앱 업데이트 후 1회). 컨테이너 루트 → `Library/Application Support` 파일 이동은 저장소 행 참조 |
| 초기화 | `resetAllData()` — 새 위치·옛 위치 파일 삭제 + 레거시 키 정리 |

```
bigramStore  = { "오늘": {"날씨": 2, "점심": 1} }
trigramStore = { "오늘 날씨": {"좋다": 2} }

입력: "오늘 날씨 " → trigram["오늘 날씨"] → ["좋다"], bigram["날씨"]로 보충 → ["좋다", "어때", ...]
```

컨트롤러 쪽 계약은 `NGramPredictiveTextProviding` 프로토콜(문장 버퍼 조작·저장 API 포함)로 추상화되어 있고,
테스트에서는 `SuggestionControllerEngineFactory`로 엔진 생성을 주입한다.

## 3. 표시 모드와 후보 갱신

### 3-1. 세 가지 모드

`performUpdateSuggestions(for:mathExpressionText:origin:)`이 다음 순서로 분기한다.

| 우선순위 | 조건 | 모드 | 버튼 배치 |
|---|---|---|---|
| 1 | `isShowMathResultsEnabled`이고 `MathExpressionCompletionEvaluator.completion(for:)` 성공 | `.mathExpression` | 0번 `"원문"`, 1번 원문+결과, 2번 결과(대치). 3칸이라 스크롤되지 않는다 |
| 2 | baseText가 비었거나 공백으로 끝남 | `.nGram` | 0번부터 예측 후보, 최대 10개 |
| 3 | 단어 타이핑 중 | `.typing` | 0번 `"현재단어"`, 1번부터 자동완성 후보, 최대 9개 |

모드는 context 추론이 아닌 `currentMode` 상태로 관리한다. n-gram 후보를 뒤 공백 없이 삽입한 뒤
context가 글자로 끝나 typing으로 오판되는 문제를 막기 위해서다.

### 3-2. 갱신 진입점

```swift
// SuggestionService
func updateSuggestions(for baseText: String, selectedText: String?, mathExpressionText: String)
```

- `baseText`: 모드 판단, 일반 예측·대치용 텍스트이자 NGram 모드의 문맥이기도 하다 (`inputBuffer` 전체
  또는 단일 단어 `selectedText`). 한영 통합 키보드도 언어 경계로 나누지 않고 같은 `inputBuffer`를 쓴다.
- `mathExpressionText`: **수식 탐지에만** 쓰는 텍스트. 일반 엔진에는 전달하지 않는다.
- `selectedText`: 수식 후보의 selection origin 기록용.

VC의 `updateSuggestions()`가 정책으로 인자를 만든다:

```
KeyboardSuggestionSelectionPolicy.suggestionUpdateAction(...)
├── selectedText 있음 + 공백 포함 → 수식으로 평가되면 .update(selectedText), 아니면 .clear
├── selectedText 있음 (단일 단어) → .update(selectedText)
└── 없음                          → .update(inputBuffer)

KeyboardSuggestionSelectionPolicy.mathExpressionDetectionText(...)
└── selectedText → inputBuffer → documentContextBeforeInput(뒤 256자) 순서로 첫 비어있지 않은 값
```

수식 탐지만 `documentContextBeforeInput` 폴백을 허용한다. 직접 입력하지 않은 텍스트라도
`=`로 끝나는 수식 계산은 유용하고 학습에는 쓰이지 않기 때문이다.

호출 시점:

| 시점 | 경로 |
|---|---|
| 키 입력/삭제 후 (반복 중 제외) | `textInteractionDidPerform` → `updateSuggestions()` |
| `textDidChange` (커서 드래그 중 제외) | selection 반영 후 갱신 |
| 커서 드래그 종료 | `primaryButtonPanStopped` |
| 삭제 팬 삭제/복구 직후 | `performDeleteButtonPanDeleteIfPossible` 등 |
| 첫 표시 직후 | `startDeferredSuggestionPreparationIfNeeded` |
| n-gram 로드 완료 | `onLoadCompleted` → 마지막 요청 재갱신 |
| TextChecker 결과 도착 (비동기, main) | `textCheckerQueue` 조회 완료 → 세대·모드가 같으면 재병합 후 delegate 전달 (§3-3) |
| undo/redo 적용 후 | `applyUndoRedoEdit` |

### 3-3. 입력 중 모드 — 두 단계 갱신과 후보 병합 (`mergeSuggestions`)

TextChecker 조회는 한 프레임보다 오래 걸리므로(12~22ms) 동기로 기다리지 않는다. `performUpdateSuggestions`는 두 단계로 갱신한다.

```
1. lexicon 결과(동기) + 직전 typing 모드의 textChecker 후보(previousCheckerTexts)를 병합해 즉시 delegate 전달
   - 이어받는 것은 textChecker 후보뿐. n-gram·lexicon·수식 후보는 이어받지 않는다
     (n-gram 후보는 입력 중 모드에서 탭되면 현재 단어를 잘못 교체하고, lexicon 후보는 이번 조회 결과로 대치돼야
     textReplacementPreviewSuggestionIndex가 어긋나지 않는다)
2. lexicon이 후보 슬롯(maxSuggestions(10) - 1 = 9)을 다 채우지 않았을 때만 textCheckerQueue(직렬, .userInitiated)에서
   textCheckerEngine.suggestions(for:limit: 9) 조회
   - 큐에 밀려 있는 동안 새 입력이 들어와 세대(textCheckerRequestGeneration)가 바뀌었으면 조회 자체를 건너뜀
3. main으로 돌아와 세대가 여전히 같고 currentMode == .typing일 때만 다시 병합해 delegate 전달
```

세대는 새 갱신마다 올리고 `clearSuggestions()`에서도 올린다. `isSuspended` 전환·모드 전환·언어 전환으로
후보를 비우면 진행 중이던 조회 결과는 버려진다. `UITextChecker` 인스턴스는 이 큐에서만 접근한다.

`mergeSuggestions` 규칙:

```
1. seen에 currentWord(lowercased)를 먼저 등록 → button1과의 중복 방지
2. lexicon 결과를 먼저 추가 (개인화 데이터 우선)
3. 남은 슬롯을 textChecker 결과로 채움
4. 최대 9개 반환 (1번 칸부터, maxSuggestions(10) - 1)
```

### 3-4. n-gram 모드 — 다음 단어 예측

`nGramSuggestions(for:)`가 엔진 결과를 최대 10개로 잘라 반환한다. 후보 바는 3칸씩
보여 주고 나머지는 가로로 넘겨서 본다. 이력이 없으면 후보 칸이 하나도 만들어지지 않는다.

n-gram 후보 탭 후에는 `updateSuggestionsAfterNGramSelection(inputBuffer:)`로 **강제 n-gram 재조회**를 한다.
방금 삽입한 것은 완성된 단어이므로 전체 `inputBuffer`를 그대로 문맥으로 넘긴다.
결과가 있으면 n-gram 모드를 유지해 연속 탭으로 문장을 이어갈 수 있고, 없으면 일반 갱신 경로로 폴백한다.

## 4. 수식 결과 모드

### 4-1. 탐지와 평가 — `MathExpressionCompletionEvaluator`

`completion(for:)`은 텍스트가 `=`로 끝날 때만 동작하며(입력 길이 256자 이하), 후보 suffix들을 순서대로 평가한다.

**후보 suffix 추출** (`expressionSuffixCandidates`):

1. 허용 문자(`0-9 , . + - * / × ⋅ x X ÷ = ( ) [ ] { }` + 공백)로 이루어진 최장 suffix
2. 마지막 줄(개행 이후)
3. `x`로 끝나는 단어 뒤에 수식이 오는 경우 공백 이후 부분 (예: `"tax 1+2="` → `"1+2="`)
4. 직전 계산 결과 토큰 이후 부분 (예: `"1+2=3 4+5="` → `"4+5="`)
5. 숫자 사이 공백으로 구분되는 뒷부분들

**평가 규칙** (`MathExpressionParser`, 재귀 하강):

- `×`, `⋅`, `x`, `X` → `*`, `÷` → `/`로 정규화. 사칙연산 + 괄호 `()[]{}`(중첩 최대 16).
- 본문에 또 다른 `=`가 있으면 실패. 숫자 구성요소 사이 공백이 있으면 실패.
- **이항 연산자가 최소 1개** 있어야 성공 (단일 숫자 `"5="`는 후보를 만들지 않음).
- 천단위 콤마는 그룹 규칙 검증 (첫 그룹 1~3자리, 이후 그룹 3자리).
- 단항 마이너스는 식 맨 앞에서만 허용. 0으로 나누기·비유한 결과는 실패.

**결과 포맷** (`formattedResult`):

- 소수 셋째 자리까지 반올림(넷째 자리에서 반올림), 천단위 콤마, 음수 0은 0으로 정규화.
- 절대값 10¹⁰ 이상이면 과학적 표기: `1.234×10¹²` (위첨자 지수).

### 4-2. 후보 구성과 action 계약

성공 시 `MathExpressionCompletion(expressionText:displayText:insertText:)`으로 세 후보를 만든다.

| 버튼 | 표시 | source | 탭 시 action |
|---|---|---|---|
| button1 | `"1+2="` (따옴표) | `.mathExpressionOriginal` | `.confirmOriginal` — 후보만 비움 |
| button2 | `1+2=3` | `.mathExpressionInsertion` | `.insertResult("3")` — `=` 뒤에 결과 삽입 |
| button3 | `3` | `.mathExpressionReplacement` | `.replaceExpression(deleteCount: 4, insertText: "3")` — `1+2=`를 결과로 대치 |

action은 `mathResultAction(at:selectedText:)`가 반환하며 **origin-aware 계약**을 따른다:

- 후보 생성 시점의 selection 상태(`MathSuggestionOrigin`)를 기억한다.
- **미선택 origin**: 현재 selection이 있으면 모든 action이 `nil`.
- **selection origin**: 현재 `selectedText`가 생성 당시 값과 **정확히 일치**할 때만 동작한다.
  생성 당시 selection이 마지막 후보 갱신의 기준 텍스트(`lastSuggestionBaseText`)와 같고 수식 텍스트(`expressionText`)로
  끝나야 한다는 조건도 함께 본다. `selectedPrefix`는 selection에서 끝의 수식 텍스트를 뺀 앞부분이다. 삽입/대치는 `.replaceSelection(selectedPrefix + …)`로 변환된다 (iOS가 selection을 통째로 교체).
- preview, 후보 탭, 스페이스 모두 같은 계약을 사용하고, 확정 대치는 `insertText` 기반이다(`setMarkedText` 미사용).

### 4-3. 스페이스와 preview 하이라이트

- 스페이스 입력 시 `mathResultAction(at: 1)`(button2 action)을 먼저 시도한다.
  적용되면 일반 텍스트 대치를 건너뛰고, 이어서 공백이 입력된다.
- `updateSuggestionPreviewHighlight()`는 수식 action이 가능하면 button2를,
  아니면 `textReplacementPreviewSuggestionIndex(baseText:)`(스페이스로 대치될 lexicon 후보)를 하이라이트한다.
  터치가 진행 중인 동안에는 preview 하이라이트를 아예 표시하지 않는다.
  `SuggestionHighlightPolicy`는 터치 > action > preview 순으로 보지만, `SuggestionBarView`가
  터치 중에는 preview 인덱스를 `nil`로 넘긴다. 탭 전용 규칙에서 시작한 후보를 벗어나 눌린
  하이라이트가 사라질 때 preview가 드러나면, 끌고 있는 동안 엉뚱한 칸이 선택된 것처럼 보이기 때문이다.
  터치가 끝나면 preview가 되살아난다.

### 4-4. 표시 조건

```
isShowMathResultsEnabled = 사용자 설정(isShowMathResultsEnabled)
                        && 호스트 허용(iOS 18+: textDocumentProxy.mathExpressionCompletionType != .no)
```

설정이 꺼지면 수식 모드 표시 중일 때 후보를 비운다.

## 5. 엔진 수명주기와 활성화 제어

### 5-1. 지연 준비

`SuggestionController.init`에서는 엔진을 만들지 않는다. 키보드 표시 속도를 위해 준비 API로 미룬다.

| API | 생성 대상 | 호출 시점 |
|---|---|---|
| `preparePredictiveEnginesIfNeeded()` | textChecker + n-gram (현재 언어) | 첫 `viewDidAppear`(`startDeferredSuggestionPreparationIfNeeded`), 이후 조회·기록 진입점마다 |
| `prepareLexiconEngineIfNeeded()` | lexicon 엔진 객체 | 위와 동일 |
| `loadLexicon(from:)` | `requestSupplementaryLexicon` 실제 로드 | 텍스트 대치가 켜져 있으면 `viewDidLoad`에서 선로딩, 아니면 첫 표시 후 |

### 5-2. 활성화 플래그

| 플래그 | 역할 | 꺼질 때 |
|---|---|---|
| `isPredictiveTextEnabled` | 자동완성 사용자 설정 | textChecker/n-gram 엔진 캐시 전체 해제 + 후보 비움 |
| `isTextReplacementEnabled` | 텍스트 대치 사용자 설정 | 대치 기능만 꺼짐. lexicon은 자동완성과 공유하므로 **둘 다 꺼졌을 때만** 해제 |
| `isShowMathResultsEnabled` | 수식 결과 표시 | 수식 모드 표시 중이면 후보 비움 |
| `isSuspended` | 텍스트 필드별 일시 중단 (`updateSuggestionBarHidden`에서 토글) | 엔진 유지, 조회·기록만 건너뜀 |

`isSuspended`를 설정 플래그와 분리한 이유: 필드 전환마다 `autocorrectionType`에 따라 빈번하게 토글되는데,
그때마다 엔진을 해제/재생성하면 n-gram 디스크 로딩이 반복되기 때문이다.

### 5-3. 식별자별 엔진 캐시 (한영 통합)

- textChecker 엔진은 `[언어코드: 엔진]`, n-gram 엔진은 `[NGram 식별자: 엔진]` 딕셔너리로 캐시된다.
  언어/식별자를 오가도 디스크 재로드가 없다. 한글/영문 키보드는 NGram 식별자가 언어코드와 같지만,
  한영 통합 키보드는 `nGramLanguage`로 고정한 `"ko-en"` 하나를 두 언어가 함께 쓴다.
- `updateLanguage(to:)`: `nGramLanguage == nil`(단독 키보드)일 때만 이전 언어 n-gram을 `saveToDisk()`로
  보존하고 `engineGeneration`을 올려 이전 언어의 비동기 로드 콜백을 무효화한다. 한영 통합 키보드는
  n-gram 엔진 인스턴스가 바뀌지 않으므로 이 둘을 하지 않고, 문장 버퍼도 전환 뒤에 그대로 유지하며
  후보 비움도 수행하지 않는다. 대신 NGram 후보를 보이는 중이면 새 언어의 선호 문자 종류로 다시 조회해
  순서가 달라졌을 때만 전달한다(입력 중 후보는 그대로).
- `releaseInactiveLanguageEngines()`: 메모리 경고 시 현재 언어가 아닌 캐시를 해제한다. 한영 통합
  키보드는 n-gram 엔진이 하나뿐이라 항상 유지되고 비활성 textChecker 캐시만 해제된다
  (단독 키보드의 비활성 n-gram 엔진은 전환 시점에 이미 저장되어 있어 유실이 없다).

상세 흐름은 [한영 통합 키보드 §5](한영%20통합%20키보드.md) 참조.

## 6. 후보 탭 처리 — SuggestionBarDelegate

`suggestionBar(_:didSelectSuggestionAt:)`는 다음 순서로 분기한다 (앞 단계가 처리하면 종료):

```
0. cancelPendingDeleteInteractions()      ← 진행 중 삭제 확정 취소
1. handleMathResultSuggestion             ← 수식 모드면 action 적용 (§4-2)
2. handleSelectedTextSuggestion           ← selection이 있으면: index 0 = 후보 비움,
                                            index 1 이상 = selectSuggestion(baseText: selectedText) 후
                                            proxy.insertText로 selection 교체
3. handleNGramSuggestion                  ← n-gram 모드면: 후보 텍스트 삽입 (아래 공백 규칙),
                                            updateSuggestionsAfterNGramSelection으로 연속 예측
4. handleCurrentWordConfirmationIfNeeded  ← index 0: 현재 단어 확정 → learnWord + recordWord + 후보 비움
5. handleInputBufferSuggestion            ← index 1 이상(최대 9): selectSuggestion(at: index-1)로 현재 단어 교체,
                                            recordWord(result.insertText)로 선택한 후보 전체를 기록
```

`selectSuggestion(at:baseText:)`는 `(deleteCount: 현재 단어 길이, insertText: 후보)`를 반환하며,
textChecker 후보면 학습하고 lexicon 후보면 대치 이력에 기록한다. baseText 마지막이 공백이면 `nil`
(n-gram 모드에서 오호출 방지 — n-gram은 `nGramSuggestionText(at:)`로 직접 가져온다).

**공백 규칙:**

| 상황 | 앞 공백 | 뒤 공백 |
|---|---|---|
| n-gram 후보, inputBuffer가 비었거나 공백으로 끝남 | ✗ | ✗ |
| n-gram 후보, inputBuffer가 글자로 끝남 | ✓ | ✗ |
| 입력 중 모드 후보 교체 / 현재 단어 확정 | ✗ | ✗ |

후보 삽입/대치에는 `smartInsertDeleteLeadingSpacePrefix`(Smart Insert/Delete)가 추가로 적용될 수 있다.
적용 후 `suggestionDidApply()` 훅이 호출되어 한글 조합 상태를 리셋한다.

### 6-1. 후보 길게 눌러 삭제

학습된 후보는 길게 눌러 자동완성에서 지울 수 있다. 시간은 `KeyboardSuggestionSelectionPolicy.removalLongPressDuration`
(0.5초)으로 고정이며 사용자 설정 `longPressDuration`과 별개다.

```
1. SuggestionBarView: 후보를 누르면 타이머 시작(scheduleRemovalLongPress).
   누른 후보를 벗어나거나 터치가 끝나면(스크롤 시작으로 취소된 경우 포함) 해제
2. 타이머 발동 → suggestionBar(_:shouldBeginRemovalAt:)
3. VC: 앱 미리보기가 아니고 removableSuggestionText(atBarIndex:)가 단어를 돌려주면
   DeleteConfirmOverlayView(클립보드 기록 삭제 확인과 같은 뷰)로 확인을 띄우고 true 반환
4. true면 그 터치는 삭제가 소비한다(isTouchConsumedByRemoval). 손을 떼도 후보를 선택하지 않는다
5. 확인 → removeSuggestionWord(_:)
```

| 메서드 | 동작 |
|---|---|
| `removableSuggestionText(atBarIndex:)` | n-gram 후보, 그리고 `canUnlearn`이 true인 textChecker 후보만 단어를 반환. lexicon 후보·수식 모드는 `nil`. 입력 중 모드는 0번이 현재 단어라 `index - 1`로 보정 |
| `removeSuggestionWord(_:)` | `nGramEngine.removeWord` + `textCheckerEngine.unlearn` 후 `currentSuggestions`에서 제거. n-gram 모드면 `updateSuggestionsAfterNGramSelection`, 아니면 마지막 요청값으로 후보를 다시 계산 |
| `NGramPredictiveTextEngine.removeWord(_:)` | 대소문자 구분 없이 unigram/bigram/trigram 전부에서 지우고 즉시 저장. 문장 버퍼는 건드리지 않고, 로딩 전이면 무시 |

확인 오버레이는 키보드 전체를 덮어 확인하는 동안 키 입력을 막고, `viewWillDisappear`에서 닫힌다.
지운 단어는 다시 입력하면 다시 학습된다.

## 7. 텍스트 대치와 복구

### 7-1. 대치 — `attemptTextReplacement(baseText:documentContextBeforeInput:)`

스페이스 입력 시(수식 action이 적용되지 않았을 때) 호출된다.

```
1. isTextReplacementEnabled + lexicon 로드 완료 확인
2. baseText의 마지막 단어와 userInput이 정확히 일치(lowercased)하는 entry 검색, 가장 긴 userInput 우선
3. ignoredShortcut와 같으면 이번 1회는 건너뛰고 ignoredShortcut 소거
4. 대치 이력(ReplacementRecord)에 기록 후 (deleteCount: userInput.count, insertText: documentText) 반환
→ VC: replaceTextWithSmartInsertDeleteSpacing으로 교체 → 이어서 공백 삽입
```

`ReplacementRecord`는 `(userInput, documentText, contextBeforeDocumentText)`를 저장한다.
`contextBeforeDocumentText`는 대치 위치 앞 문맥(최대 256자, `KeyboardTextContextNavigator.maximumCursorRestoreDistance`)으로,
복구 매칭을 엄격하게 만든다. 이력은 최대 20개(`maxReplacementHistoryCount`).

### 7-2. 복구 — `attemptRestoreReplacement(inputBuffer:documentContextBeforeInput:selectedText:)`

삭제 버튼 입력 시 일반 삭제보다 먼저 시도된다.

```
1. selectedText가 있으면 복구하지 않음 (선택 삭제 우선)
2. 이력을 최신부터 역순 탐색: (contextBeforeDocumentText + documentText)가
   inputBuffer의 suffix와 일치하면 매칭. inputBuffer가 비었으면 documentContextBeforeInput으로 폴백
3. 매칭된 record 제거 + ignoredShortcut = userInput 설정
4. (deleteCount: documentText.count, insertText: userInput) 반환
→ VC: replaceText로 원래 단축어 복원
```

### 7-3. ignoredShortcut — 재대치 방지

```
"ㅈㄱㅈ" + 스페이스 → "지금 가는 중!"으로 대치
→ 삭제 → 복구 → ignoredShortcut = "ㅈㄱㅈ"
→ 다시 스페이스 → 같은 단축어 대치 1회 건너뜀 (ignoredShortcut 소거)
```

초기화 시점: 스페이스 이외의 모든 키의 `textInteractionWillPerform`에서 `clearIgnoredShortcut()`.
(복구를 수행한 삭제는 훅 이후에 다시 설정하므로 유지된다.)

대치 이력 초기화: 리턴 입력, undo/redo 적용, 클립보드 기록 패널에서 텍스트 붙여넣기(둘 다 `undoRedoEditDidApply`),
텍스트 필드 전환(undo 이력 무효화 시). 한영 통합 키보드의 한/A 전환은 대치 이력을 비우지 않는다
([한영 통합 키보드 §3](한영%20통합%20키보드.md)).

## 8. 학습·기록 시점

### 8-1. UITextChecker 학습

| 동작 | 학습 | 이유 |
|---|---|---|
| button1 탭 (현재 단어 확정) | ✓ | 사용자가 의도한 단어 |
| textChecker 후보 선택 | ✓ | 사용자 선호 반영 |

| n-gram / 수식 후보 선택 | ✗ | 별도 관리 |

### 8-2. n-gram 기록

한영 통합 키보드도 언어 경계로 나누지 않고 전체 `inputBuffer`를 그대로 쓴다.

| 동작 | 기록 |
|---|---|
| 스페이스 (`insertSpaceText`) | `recordUncommittedWords(from: inputBuffer)` — 전체 버퍼 단어 수와 문장 버퍼 수를 비교해 미기록 단어 일괄 기록 |
| button1 탭 (현재 단어 확정) | `KeyboardSuggestionSelectionPolicy.currentWordForConfirmation(inputBuffer:)`이 구한 현재 단어를
  `learnWord`로 학습하고 같은 단어를 `recordWord`(NGram)로 기록한다 |
| 입력 중 모드 후보 선택 | 선택한 후보 텍스트 전체를 `recordWord(result.insertText)`로 통째 기록한다. 여러 단어로 된 후보(예:
  `"On my way!"`)도 공백을 지우지 않고 그대로 기록한다(의도된 동작) |
| 리턴 (`insertReturnText`) | `endSentence(inputBuffer: inputBuffer)` — 전체 버퍼의 미기록 단어 기록 후 문장 버퍼 초기화 + 디스크 저장 |
| 키보드 사라짐 (`viewWillDisappear`) | `saveNGramData()` |

한글/영문이 공백 없이 섞인 토큰(`SY키보`)은 언어별로 쪼개 기록하지 않고 `UITextChecker`/`inputBuffer`
단위로 한 단어처럼 다뤄지므로 단어 완성이 약하다. 타이핑 중 NGram 완성(#158)이 이를 보완할 예정이다.

### 8-3. 삭제와 문장 버퍼 동기화 (`deleteText()`)

`BaseKeyboardViewController.deleteText()`가 삭제 전후 `inputBuffer` 상태로 직접 판단한다(별도 Policy
없이 인라인 분기).

```
전체 inputBuffer가 비워짐             → resetSentenceBuffer()   (문맥 전체 리셋)
스페이스를 지워 단어 경계가 허물어짐   → removeLastRecordedWord() (마지막 기록 단어 pop)
```

`resetInputBuffer()`(커서 이동, 필드 전환, 키보드 열림/닫힘)도 `resetSentenceBuffer()`를 함께 호출한다.

## 9. 한글 입력과의 접점

- 한글 조합의 모든 proxy 편집은 Base 래핑 메서드를 거치므로 `inputBuffer`에는 조합 완료 문자열만 들어온다.
- 스페이스 순서: **수식 action → 텍스트 대치 → `insertSpaceText`(n-gram 기록 + 공백)**.
  천지인 조합 확정 스페이스는 `super.insertSpaceText()`를 타지 않으므로 공백·n-gram 기록이 없다.
- 삭제 순서: **대치 복구 → 한글 자소 분해 삭제**.
- 후보/수식 적용 후 `suggestionDidApply()`가 한글 조합을 리셋한다.
- `shouldDeferUndoRedoCommit`(조합 중) 동안 undo 그룹 확정이 미뤄진다.

상세는 [한글 입력 로직 §10](한글%20입력%20로직.md) 참조.

## 10. SuggestionBar 표시 제어

SuggestionBar는 후보 영역·undo/redo·클립보드 세 요소를 얹는 툴바다.
세 요소가 각각 독립적으로 바를 유지시키며, 바 전체 표시와 후보 영역 표시를 따로 판정한다.

```
후보 영역 사용 가능:
  자동완성 켜짐 ∧ autocorrectionType != .no

바 숨김 조건 (KeyboardPresentationStatePolicy.shouldHideSuggestionBar):
  currentKeyboard == .tenKey
  ∨ (후보 영역 사용 불가 ∧ undo/redo 꺼짐 ∧ 클립보드 기록 꺼짐)

후보 영역 숨김 조건 (KeyboardPresentationStatePolicy.shouldHideSuggestionButtons):
  바 숨김 ∨ 후보 영역 사용 불가
```

- 규칙은 하나다. **바 안에 쓸 수 있는 것이 하나라도 있으면 보인다.**
- 세 요소 모두 설정이 켜져 있으면 표시한다는 같은 규칙을 따른다. 앱 미리보기도 예외가 아니다.
  미리보기는 실제 키보드와 같은 모습을 보여주되 클립보드 패널만 열지 않는다
  (`suggestionBarDidTapClipboard`에서 차단). 클립보드 기록의 실제 읽기·쓰기는
  `isClipboardHistoryAvailable`이 Full Access와 미리보기 여부까지 따로 본다.
  후보를 못 쓰는 이유가 자동완성 설정 OFF인지 텍스트 필드 차단인지는 구분하지 않는다.
- 후보 영역만 비울 때 클립보드·undo·redo 버튼의 위치와 폭은 그대로 둔다
  (`SuggestionBarView.updateSuggestionArea(isVisible:)`가 후보 사이 divider만 숨긴다).
  후보가 하나도 없는 상태와 같은 모습이므로 별도의 레이아웃 규칙이 없다.
- 후보 영역이 숨겨지면 `isSuspended = true`로 조회·기록만 중단한다 (엔진 유지).
  바가 보이는 상태에서도 후보 영역만 숨겨질 수 있으므로 `isSuspended`는 바 표시 여부와 별개다.
  `isSuspended`는 `false → true` 전이에서만 후보를 비우고 진행 중 TextChecker 요청을 세대 증가로 무효화한다
  (`.no` 필드에서 키 입력마다 같은 값이 재대입되기 때문. `true → false`에서는 비우지 않는다).
- 바 표시 상태가 바뀌면 키보드 높이를 재계산한다. undo/redo나 클립보드 기록을 켠 상태에서는
  `autocorrectionType`이 바뀌어도 바가 유지되므로 높이가 변하지 않는다.
- 앱 설정의 키보드 높이 미리보기는 `자동완성 ∨ undo/redo ∨ 클립보드 기록`으로 바 자리를 계산한다.
  실제 바 표시 규칙과 같아야 미리보기 높이와 실제 키보드 높이가 어긋나지 않는다.
- undo/redo 버튼은 SuggestionBar가 보이고 `isUndoRedoEnabled`일 때 표시된다. 자동완성 설정과는 독립이다.
  → [삭제와 실행취소 로직](삭제와%20실행취소%20로직.md)
- 후보 버튼(`SuggestionButtonView`)은 가로 스크롤 없이 두 줄 표시·글자 크기 축소·중간 생략으로 긴 후보를 처리한다.
  이는 의도된 UI 계약이다 (버튼 안에 스크롤 컨테이너를 도입했다가 롤백된 이력이 있다).
- 후보 영역은 후보가 몇 개든 **항상 3칸으로 보인다.** 버튼 폭은
  `(뷰포트 폭 - divider 두께 × 2) / 3`이고, divider는 버튼 개수가 아니라 이 열 격자를 따른다
  (`SuggestionDividerPolicy.dividerCount(forSuggestionCount:)` = `max(후보 수, 3) - 1`).
  후보가 3개보다 적어도 빈 칸에 divider가 남아, 그 자리를 눌렀을 때 앞 후보가 적용될 것처럼 보이지 않는다.
  맨 앞과 맨 뒤에는 두지 않는다.
- **경계 divider는 인접한 후보가 하이라이트되면 지운다.** 어느 쪽 끝 후보를 누르고 있는지
  구분되게 한다. 어느 divider를 지울지는 `SuggestionDividerPolicy.clearedDividers(...)`가 정하고
  뷰는 결과만 색으로 적용한다. 후보가 3칸을 채우지 못하면 마지막 후보는 오른쪽 끝 divider와
  인접하지 않으므로 경계 판정에서 제외하고(`suggestionCount >= visibleColumnCount`), 스크롤로
  뷰포트 밖에 나간 버튼은 뷰가 `isHighlightedSuggestionVisible: false`로 넘겨 걸러낸다.
- 후보가 갱신되면 `updateSuggestions(currentWord:suggestions:)`가 `applyHighlights()` 뒤에
  `updateDividers()`를 불러 divider 색을 함께 갱신한다. 숨어 있던 divider가 새로 보일 때
  직전 하이라이트의 `.clear`를 들고 나오지 않게 한다.
- **후보 선택 방식은 후보가 뷰포트를 넘치는지로 갈린다.** 판정은 후보 개수가 아니라
  `SuggestionBarView.isSuggestionAreaScrollable`(= `contentSize.width > 뷰포트 폭 + 허용 오차`) 하나다.
  - 넘치면 **탭 전용**이다. 끄는 동작이 스크롤이므로 시작한 후보에서 떼야만 선택하고,
    벗어나면 하이라이트도 지운다.
  - 넘치지 않으면 `UIScrollView`의 pan이 시작되지 않으므로 **끌어서 고르기**를 그대로 유지한다.
    수식 3칸도 여기에 해당한다.
  - 이 규칙은 터치가 시작될 때 한 번 정해 그 터치 동안 유지한다. TextChecker 후보가 늦게 도착해
    터치 도중 후보 개수가 바뀌어도 같은 터치가 두 규칙을 오가지 않는다.

## 11. 메인 앱 — 학습 데이터 초기화

`SYKeyboard/Presentation/KeyboardSettings/PredictiveTextSettingsView.swift`에서
`SuggestionController`를 거치지 않고 엔진을 직접 생성해 초기화한다 (초기화는 설정 앱 전용 동작).

```swift
private let supportedLanguages = ["ko-KR", "en-US"]
private let nGramLanguages = ["ko-KR", "en-US", NGramPredictiveTextEngine.hangeulEnglishLanguage]  // "ko-en" 포함

for language in supportedLanguages {
    TextCheckerPredictiveTextEngine(language: language).unlearnAllWords()  // 시스템 사전 학습 해제
}
for language in nGramLanguages {
    NGramPredictiveTextEngine(language: language).resetAllData()           // n-gram 파일 삭제
}
```

n-gram 초기화는 한영 통합 키보드가 쓰는 `"ko-en"` 식별자까지 별도 목록(`nGramLanguages`)으로 돈다.
TextChecker는 언어별(`supportedLanguages`)로만 돈다(통합 전용 TextChecker 인스턴스는 없다).
두 저장소 모두 App Group을 사용하므로 다음 키보드 세션부터 반영된다.
